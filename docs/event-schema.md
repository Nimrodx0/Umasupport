# イベント到達条件スキーマ v1（2026-10-16）

## 目的と現在の実装範囲

選択式イベント、選択肢なしイベント、連続イベント、打ち切り、成功・失敗によって異なる**獲得候補**を機械可読にする。

**今回のスキーマとテストは架空データで検証した。公開版は今も通常ヒントのみで、実ゲームのイベントは未収録。** イベントを扱えるようになったこととイベントデータを取り込んだことを混同しない。

## 2026-10-19更新：外部出現条件と連続イベント内部の分岐を分離

**外部出現条件は対象外**：ランダムなイベント発生率・絆・ターン等の再現は要求しない。

**連続イベント内部の条件は必須**：親イベントの選択肢によって次段の選択肢・報酬・進行／打ち切りが変わるとき、`requires` と `terminal` を設定し、到達不可のイベント報酬を集計しない。前段の選択を変えたら従属する後段の選択を消去する。別の後段A／後段Bをそれぞれ異なる親 `choiceId` に接続可能。

親 `choice` イベントの `requires` に `choiceId` を省略した場合、いずれかの**選択済みかつ非打ち切り**選択肢で継続することを表す。どの選択肢でも続くと資料で確認できない限り、`choiceId` を省略して分岐を推測しない。

**到達条件の現在の実装**：結果 `outcomeId` による次段への到達条件も機構として実装済み（後述）。一方、外部ソースの結果依存情報が欠けたイベントを「経路再現済み」とみなすことはできない。PR #106の数値ファクト879件には連続内分岐の検証済み構造がない。

## 2026-10-24：非スキル報酬の分岐付き保持（非公開技術試作）

スキル報酬`rewards[]`は従来の数値スキルIDの候補集計に専用とし、能力値・体力・やる気・絆・スキルPt・適性Ptは**独立した`effects: [{kind,delta,sourceComponent?}]`**で扱う。イベント本体、選択肢、各`outcomes[]`へ記載できる。結果未確定なら複数結果の各効果を**条件付き候補**として残し、獲得済み値には集計しない。

`kind`は`speed`/`stamina`/`power`/`guts`/`wisdom`/`energy`/`max_energy`/`mood`/`bond`/`skill_points`/`aptitude_points`に限定。`delta`は正負の非0整数、`sourceComponent`は`event-result`/`scenario-bonus`または省略。同じ能力への元報酬とシナリオ追加分は別記録とし、同一能力・同一成分の二重登録は拒否。同じ親で`effects`と`outcomes`は併用不可、結果が複数の場合は各結果に必要な成分を置く。

`availabilityKind:'scenario-overseas'`は海外の発生条件を**獲得候補の条件ラベル**として扱うだけで、出現確率はモデル化しない。`UmaCore.directEffectRoutes`はスキル経路と別の結果別一覧を返し、`directRoutes`・`aggregate`に新たなスキル提供枚数を生まない。実出典の一例は[佐岳メイのR/SSR非公開2カード×2結果の検証](phase2-nonskill-outcome-runtime-20261024.md)。**旧非公開2,512件は不変、公開イベント0件**。公開JSONへの転送・正式収録を意味しない。

## 2026-10-24：効果の受け手と全件数値監査

非スキル効果の `effects[]` は `recipientCharId`（正の整数、省略可）を扱う。これは元GameToraの絆 `char_id` の対象を保持する数値であり、キャラクター名を推測しない。同じ種類・成分でも受け手が違えば別の効果。同じ種類・成分・受け手の重複は拒否する。`core.directEffectRoutes` もIDを維持。

[GameTora全2,488イベントの数値監査](phase2-gt-whole-nonskill-effect-audit-20261024.md)では、2,181イベントについて非スキル効果の匿名・孤立した形状だけを変換した。連続経路の完全性、シナリオ条件、公開承認は別に審査する。

## 2026-10-25：状態の付与・回復候補を数値効果と分離

イベント・選択肢・結果の末端には、従来の数値`effects[]`とは**独立**した`statusEffects[]`を任意で持たせる。`{kind:'add-condition',conditionId:10,possible:true}`は状態ID10の付与**候補**、`{kind:'cure-one-bad',possible:true}`は保有する悪い状態のうちランダムに**1つ回復する操作候補**。出典に明示された場合のみ`chance`（0超1以下の数）を保持。元コードに隠れた個別の状態適用条件・確率・治療対象の選択は、出典に明記された範囲以上の保証をしない。状態効果は能力値増減でもスキル取得でもないため、`UmaCore.directStatusRoutes`は必ず`possible:true`かつ`conditional:true`で返す。状態操作・効果を同じ結果の末端に併記できるが、結果分岐の外へ移動して無条件取得にはしない。

## 2026-10-25：GameToraの結果別`chain_end`の確認と非スキル報酬の結合

固定GameToraの`chain_end`は、その**結果**で後続の連続イベントを打ち切ることを示す。単なるイベント全体の終了や他の結果の継続停止とは区別する。非公開非スキル構造プレビューは`section:'arrows'`かつパラメータなしの`chain_end`だけを該当する結果・選択肢の`terminal:true`として保持する。それ以外の制御マーカー、前段結果条件や状態による異なる進行は勝手に解釈しない。

非スキル元とスキルイベントを結合する際は、カードID・元イベント・選択肢・結果／OR派生を確実に照合した上で、**双方の`terminal`値が正確に一致する場合だけ**数値効果・状態操作・動的効果を移す。スキル側`requires`や`terminal`は一切書き換えず、スキル報酬のSHA不変を検査する。[打ち切り109記載の固定全件監査](phase2-gt-chain-end-outcome-proof-20261025.md)により、91記載を出典由来の終了として解釈し、非スキル技術構造化が2,309→2,395件となった。**元ゲームの全連続条件再現・正式公開は未完了**。

## 2026-10-26：同一結果で同じ対象へ数値効果が繰り返される場合

`effects[]`には同じ能力・同じ受け手の数値報酬が別の元GT効果行として記載される場合がある。このとき元効果の`sourceEffectOrdinal`（各結果の元GT効果配列で**1から数えた位置**）を両方へ付け、正整数の元位置が重複せず増加順に並んでいる場合だけ、同じ種類の複数効果を受け入れる。元位置が不明・欠損・逆順・重複なら拒否する。単なる加算済みの1行への書き換えはしない。

`all_stats`の1行は5能力への構造展開となるが、重複する個別能力行の元位置が一致していないか確認する。絆効果の異なる受け手を勝手に同一にしない。`UmaCore.directEffectRoutes`は元の`sourceEffectOrdinal`を返す。**体力・やる気の上限を含む最終値のシミュレーションや適用完了を保証しない**。単純な符号付き報酬を既存イベント結果へ非公開で統合する際も、スキル取得候補と連続条件は元SHAで不変検証する。

[固定GT2,488件の追加監査](phase2-gt-ordered-repeated-numeric-effects-20261026.md)では、重複効果25記載のうち他に保留理由のない10記載を活用し、非スキル構造化2,395→**2,402件**、既存2,512件中の結合2,394→**2,401件**。正式公開0件は不変。

## データ構造

最上位は schemaVersion=1、cards の配列。それぞれ cardId、events を持ち、coverageStatus は partial（既定）または complete。

カードの cardId はカード辞書の実IDと一致させ、名前の類似で推測しない。

イベントの定義：
- id、name、type は必須。type は auto または choice。
- choice は choices 配列（各要素 id、label、任意の terminal、rewards、outcomes）を持つ。未選択なら報酬を集計しない。
- auto は、到達できれば直接の rewards を自動集計する。
- requires: {all:[{eventId,choiceId?},...]} は全条件を満たすと到達できる。親が choice なら選択済みかつ非打ち切りが必須。特定選択だけを要求するときは choiceId を明示し、すべての非打ち切り選択から進めると資料で確認できた場合にだけ省略可能。親が auto なら choiceId 不要。古い架空fixture形式の単一 requires:{eventId,choiceId} も認識する。
- terminal:true を選んだ場合は、後続イベントが到達できない。打ち切りルートから後続に接続する不正データは拒否する。
- rewards は {skillId,level?,condition?}。outcomes は id、label、rewards を持つ2つ以上の排他的候補。「成功」「失敗」の報酬をどちらも条件付き候補として扱い、確率や実際の獲得を保証しない。
- `outcomeId` を用いた後続イベント・選択肢の到達条件は実装済み。`requires.all[]` 内で前段の `eventId` と `outcomeId` を指定し、選択式の親なら `choiceId` も指定する。結果が未確定なら候補を条件付き、結果が食い違えば到達不可とする。出典にない結果条件を推測で追加することはできない。

## 友人サポカのお出かけ開始と拒否（現行スキーマの表現）

お出かけを解放するランダムイベントの選択肢／結果と、その後のお出かけ `dates` は、通常の`arrows`連続イベントとは**異なる種類の連続関係**。開始イベントの拒否や失敗に `chain_end` がある場合は、`terminal:true` を**その選択肢または結果に限って**記述する。終了しない可能性のある結果にまで`terminal`を広げない。

元の開始イベントが独立して確認された場合、最初のお出かけ `dates` に`requires:{all:[{eventId:開始イベントID}]}` を付け、2件目以降は直前のお出かけに依存させる。`choiceId`がない親参照は「選択済みの非打ち切り経路なら継続」を表すため、拒否時と終了結果選択時は`core.reachability`が`blocked`を返す。結果が未確定なら後続報酬は条件付き、親の選択自体が未確定なら後続はまだ到達不可であり、無条件獲得としない。外部の発生率は依然扱わない。

元の`random`には無関係な通常イベントもあるため、**すべてのランダムイベントに同じルールを適用してはならない**。現在の技術用変換器が自動連結を試すのは、同一カードにお出かけ系列があり、通常`arrows`がなく、複数選択肢を持つ唯一のランダム終了イベントから非終了経路を確認できる場合のみ。複数の終了候補や意味論が不明な場合は全体を保留。開始イベント自体のスキル報酬が未解析なら、その後のお出かけも成功扱いにしない。

固定ソースでの実際の分類・適合数は[個別監査](phase2-outing-unlock-terminal-review-20261021.md)と[開発状況](status.md)を参照。技術スキーマが表現できることと、現行ゲームで検証・公開承認されたことは別。

## スキルヒントと直接習得・マイナススキル付与の区別

イベント報酬 `rewards[]` の省略可能フィールド `kind` は、**省略または`hint`**（従来どおりヒント獲得）、`obtained`（通常のスキル自体を習得）、`negative`（マイナススキル付与）の3種類。`obtained`と`negative`にヒントLv `level` を付けてはならず、バリデータが拒否する。スキル数値IDの所属する UmaSim `rarity` と報酬種類も整合必須。`negative`を数値スキルIDで照合した際は`minus`分類のみ受け入れ、通常ヒントへ名寄せしない。

イベント分岐の選択・結果による到達判定はこれまでと同じだが、**マイナススキル付与を有益な提供スキルとして`core.directRoutes`と`aggregate`に加えない**。イベントの選択肢／結果表示には「マイナススキル付与」を明示する。これにより目標スキルのカバー率は増えない。正の`obtained`（直接習得）はヒントLv無しで候補に入り、区別した名称で表示する。

この機能を導入した根拠は[固定GameToraの直接付与全件監査](phase2-negative-skill-grant-schema-20261021.md)。固定版の直接付与7効果は**全て`minus`**であるが、これは最新ゲーム全体の習得種類を制約する事実ではない。文面・画像・正式公開の別ゲートを通していないため、本番用イベントJSONに自動収録しない。

## 先行結果に依存する後続スキル報酬（結果の排他性）

後続のイベントだけでなく、`outcomes[]` の個々の結果にも `requires:{any:[{all:[{eventId,choiceId?,outcomeId?},...]},...]}` で**過去の選択肢と結果の組合せ**を記録できる。AND配列の一つでも不一致なら、その結果は到達不可。いずれのOR節も成立しないなら表示・報酬集計しない。結果が未指定なら「条件付き候補」であり、成功率やヒントLvを無条件としない。

マチカネタンホイザの固定元には前段2イベントの成功／失敗の4組合せから同一スキルのヒントLv3／2／1を選ぶ経路がある。エルコンドルパサーでは「前段の上選択肢**かつ成功**」の場合だけLv3、それ以外はLv1。この条件は [固定スナップショットと独立資料の個別監査](phase2-final-three-outcome-review-20261021.md) を前提に、該当カード・結果順序・数値IDがすべて一致する技術用モデルへ限定して追加した。別カードのゲーム規則として一般化しない。

また、1つの元データ結果に同一ヒントブロックが重複する場合は、**単に同一IDを重複排除したり、Lvを加算したりしない**。元ブロックが完全一致し、別資料で実際の各ヒントLvが1回ずつと確認できたケースのみ、スキル候補を1回分とし、元の重複記載数を監査で保持する。能力値・絆・やる気など、本アプリのスキル投影で対象外の効果は再現済みとは呼ばない。

## 照合・件数計測とフェイルクローズ

poc/src/event_schema.js の validateCatalog(catalog, model) は、登録済みカードID／スキルID、重複イベントID、未定義の親、循環、打ち切りから後続への接続などを検査し、不正なら全入力を拒否する。

戻り値の totalModelCards、cardsWithRecords、eventsWithRecords、perCard[cardId] は**入力カタログに何件含まれるか**だけを表す。実ゲーム上の全イベントの網羅率とは異なる。coverageStatus=complete は入力元の申告であり、第三者に確認された完全性ではない。

poc/src/core.js は親イベントの到達可否を連鎖的に評価する。先行分岐未選択・打ち切りルートの場合は報酬を計上しない。提供枚数は、同カードに複数経路があっても1枚。

## 実ゲームデータ導入の条件

- 第三者公開元のイベント文とゲームデータの利用条件を確認する。単なる公開・閲覧可能を再配布権限や再利用許諾とみなさない。
- イベントレコードとUmaSimのカードゲーム内IDを一致させ、ゲーム内での連続順と打ち切り・成功失敗を個別検証する。
- スキル辞書にないイベント固有スキルや金スキルの正式IDを整備する。未収録IDを根拠なしに通常ヒントへ一致させない。
- 取得・変換・キャッシュ戦略はデータソース別に独立して評価する。UIへの手動更新ボタンは設けない。
- 現段階では、取得先の条件や対応表が確定していないため公開版に第三者イベントデータを追加しない。

## 外部イベントソースとの接続

[実ソース照合記録](event-source-audit.md) にID一致・例外・スキル未照合をまとめた。`poc/src/event_review_compiler.js` は、個別イベントの到達・打ち切り・報酬条件を `chainVerified:true` と `rewardSemanticsVerified:true` でそれぞれ確認し、数値スキルID対応も明示したの場合に限ってスキーマv1を出力する。元JSONの `defaultChoiceId` を育成で選択済みのルートとみなしてはいけない。

## 選択分岐に依存しない連続継続（2026-10-16、PR #20）

従来の `requires:{all:[{eventId,choiceId}]}` に加え、**親が選択式でも** `requires:{all:[{eventId}]}` を記述できるようにした。この場合「親の選択肢が実際に一つ選ばれ、かつ打ち切りではないなら後続へ進む」意味。未選択、打ち切りは後続へ進まない。すべて打ち切り選択肢の親をこの形で参照することは検証エラー。`src/core.js` の実行時判定と検証器を一致させた。

このルールはイベントの発生率や成功失敗の自動確定を意味しない。Game8の欠損4枚の**検証用候補**と、残り1枚の未確認記録は [Game8のSSR欠損監査](game8-missing-ssr-review.md) を参照。

## 2026-10-18：結果分岐のレビュー済みオーバーライドと公開条件（PR #67）

`src/event_review_compiler.js` で第三者候補JSONを公開JSONへ変換する際、イベントごとの `chainVerified:true`（到達条件）、`rewardSemanticsVerified:true`（報酬）、`selectionSemanticsVerified:true`（選択式か自動発生か）、`publicationReviewed:true`（出典・転載等の公開可否）を**それぞれ独立して要求**する。候補配信の `selection=auto` は計画用の分類であり、これを検証せず実ゲームでの無条件取得へ変換してはならない。

候補が `selection=single` の場合、レビュー入力の任意項目 `choiceOutcomeReviews` で**各選択肢の複数の結果別報酬**を指定できる。例は架空のIDと名称のみ：

~~~json
{
  "sourceEventId": "evt_30242_1",
  "cardId": "30242",
  "chainVerified": true,
  "rewardSemanticsVerified": true,
  "selectionSemanticsVerified": true,
  "publicationReviewed": true,
  "choiceOutcomeReviews": {
    "go": [
      {"id":"success","label":"成功","skills":[{"skillId":2001,"skillName":"架空速度","hintLevel":1}]},
      {"id":"great","label":"大成功","skills":[{"skillId":2001,"skillName":"架空速度","hintLevel":5}]}
    ],
    "stop": [
      {"id":"success","label":"成功","skills":[]},
      {"id":"great","label":"大成功","skills":[]}
    ]
  }
}
~~~

この入力は**既存の候補レコードにあるすべての選択肢に対する結果リストが揃う場合だけ**受け付ける。欠落・余分なID・重複結果・2種類未満の結果・未承認のスキルID/名称を拒否する。外部候補にある既定選択・平坦化報酬を併用せず、承認済み結果だけを公開スキーマの `choices[].outcomes` へ変換する。実行時の `core.directRoutes` はどの結果のスキルも **conditional=true** として扱い、成功・大成功双方のLvを区別する。

`choiceOutcomeReviews` なしの場合は既存の選択枝の `rewards` を維持するが、上記4承認の省略は認めない。レビュー入力は第三者が公表するイベント本文から自動生成されるものではない。独立の検証と公開許諾の審査が必要。今回の検証は人工イベントだけで、SSR30311等の実イベントは**0件のまま**。

## 2026-10-18：無条件報酬と結果別報酬の混在拒否（PR #69）

公開イベントスキーマv1の同じイベント／選択肢に `rewards`（結果条件なし）と `outcomes`（成功・大成功等の排他的な結果候補）が同時に指定された場合、**データ全体を検証失敗として拒否**する。外部候補に「大成功のみのスキル」が平坦化されたまま残った状態で、成功・大成功の結果を追加すると、大成功のスキルが無条件でも獲得できるかのように集計される危険があるため。

共通の報酬がある場合も各レビュー済み結果の `outcomes[].rewards` に明記し、未検証の共通報酬を勝手に確定扱いしない。既存の正常な架空イベント・条件付きの集計は維持。ブラウザ公開JSONを取り込む `public_event_catalog.attach` でも破損入力の**原子的拒否**を人工テストし、通常ヒントと以前の承認済みイベントを保護する。この変更は実イベントの公開承認やゲーム内結果確率の確定ではない。

## 2026-10-19：結果依存／選択肢依存の到達判定を実装（PR #108）

- 以降はこの追記が本文中の「`outcomeId` 未対応」という旧制約に優先する。`requires.all[]` へ `outcomeId` を追加できる。選択式の親では `choiceId` を併記。参照結果の `terminal:true` と未定義IDは検証失敗。
- `choice` の個々の `choices[].requires` によって、同じ後続イベント内でも表示・操作可能な選択肢を制限できる。イベントへの到達と選択肢への到達を独立判定し、選択肢の自己参照・依存循環は拒否。
- 結果が未選択なら後続は `conditional`、確定した失敗などで不可能なら `blocked` とする。スキル集計は到達可能性に矛盾する古い選択状態を除去し、`conditional` の報酬には根拠条件を残す。
- `outcomes` の選択状態はデッキ枠に任意マップとして保存し、前段の選択・結果を変更したら従属する結果・選択を再帰削除。従来の `outcomes` なし設定は読み込める。
- テストは `poc/tests/outcome_dependent_branches.test.cjs`。これは人工グラフの機構テストであり、563枚の実ゲーム分岐の照合ではない。全件監査索引は `phase2-result-branch-and-roster-index-20261019.md` に記録。公開イベント0件を維持。
