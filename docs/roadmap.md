## 最終目標とスコープ

全対象サポートカードについて、本育成・継承育成のデッキを手動作成・比較し、**通常ヒント、イベントの選択肢／結果／後続分岐、スキル階層、重複、目標カバー**を確認できるWebアプリ。自動最適化・サポカ以外の経路・イベントの外部的な発生確率は対象外。詳細は [requirements.md](requirements.md)。

## 工程（A／B／Cを独立判定）

| Phase | 目標 | 次の完了条件 |
| --- | --- | --- |
| 0 基盤 | GitHub Pages、取得検証、キャッシュ・CI | 再現可能な手順、ソース障害時の復旧と本番同等の環境確認 |
| 1 カード・スキル | 全サポカ、通常ヒント・階層・ヒント性能・表示順 | 対象母集団全数の独立裏付けと例外分類、Pagesと物理端末確認 |
| 2 イベント | 全カードのイベント・選択・結果・内部連続条件・報酬 | 対象カードで実イベントの収録範囲を分類、数値と分岐を監査、独自公開データと公開ゲート・操作試験 |
| 3 利用者機能 | デッキ、保存、逆引き、所持、目標・検索 | F-01〜F-09のA/B/C受け入れを全対象に実施 |
| 4 統合検証 | 取得障害、UI、データ更新、設定復元 | [verification-plan.md](verification-plan.md) の異常系・端末マトリクスを完了 |
| 5 正式公開 | 権利・更新・ロールバック・運用 | 配布条件、サポート体制、公開版の全件証拠を確認 |

A＝機構テスト、B＝固定元と独立ソースの全件監査、C＝実アプリと物理端末の操作・表示。**一軸だけ成功しても工程完了にはしない。** ゲート詳細は [verification-plan.md](verification-plan.md)。

## 依存と当面の優先順

**2026-10-29最新方針：サービス完成を優先し、イベント取得は第三者GitHubのGameTora派生JSONへ復帰する。** 新規サポカをUmaSim全カード名簿の差分で検出し、`systemless10/UmamusumePS` の対象 `support_<ID>.json` を固定コミットで取得・検証して独自DBへ**増分追加**する。既存カード・イベント・ユーザー設定・承認記録の全件再生成／上書きは禁止。元JSONの更新が遅れている新カードは、イベントが存在しないのではなく**未入手／保留**と明示し、別のカードの機能完成を妨げない。

**GameTora本体HTMLの汎用直接取得器は未完成のまま開発保留**とする。試験コード・根拠資料は残すが、これの完成・構造別100%解析・Chrome再実測は、以下の製品作業やGitHub派生JSONの採用の先行条件ではない。2026-10-27の直接取得への全面移行方針、および2026-10-29午前の「直接取得器を必ず完成させてから下工程へ」という依存を**撤回**する。旧実証の数字を派生DB品質の保証に転用しない。

### 現在の製品完成への作業順（必須）

**2026-10-30、既存Phase 2の続きから再開する**。新カード監視・変換器の実装成功と、既存563カードのGameWith照合・欠損補完の完了は別工程。現在の**未完タスクの唯一の入口**は[Phase 2残件台帳](phase2-open-items.md)。各作業開始時に当該行と**後続の訂正文書**を読み、既に解消した欠損をもう一度調査したり、非公開候補が公開0件であることだけから公開ゲート実装へ飛ばない。

1. **既存Phase 2の出典差異・欠損の残件を整理・補修**：GameTora由来の固定2,488件＋GameWithで20件等を補完した**非公開2,512イベント**を出発点とし、[未解決台帳](phase2-open-items.md)のP2-01〜P2-04を優先。SSR30240の同一カード版・連続3段階、Checker P2未同定11位置、SR20075の分岐差、佐岳メイ海外イベントの採用範囲を、すでに確認した事実と未掲載の事実に分ける。GameWithに記載のない値・条件を創作せず**項目別に保留**する。既にGameWithで確定した4SSR20件・SSR30221連続3段階・SSR30180ヒントなどを再裁定しない。
2. **既存の統合候補とスキル獲得の不変条件を再照合**：P2-05〜P2-07にある非スキル一般変換の保留16元イベント・SSR30080の非スキル結合差・旧固定辞書での未確認属性を確認。**スキルID／Lv、選択／排他結果、連続内部の打ち切り・到達条件へ影響するもの**から共通規則で補う。既存の技術変換成功率やスキル無関係の報酬まで「全件収録済み」と言わない。対象外・元資料未掲載は具体的な理由付きで保留できる。既存DBの全件再生成・上書きは禁止。
3. **残件の確定と公開可能範囲の判定**：上記の分類と非公開2,512件の本番ローダー検証を再計測し、完了／明示保留／新たに発見した差異の数を元出典版・対象分母付きで報告する。その後に[既存の公開イベントゲート](checker-public-catalog.md)・表示・出典利用条件のレビューを行い、**承認済みの独自データだけ**を公開用DBに追加する。通常8イベントを使った[公開追記リハーサル](phase2-first-event-release-rehearsal-20261030.md)は下流の既存技術として保管し、これを先に深掘りしてPhase 2欠損調査を迂回しない。
4. **利用者機能と実環境の受け入れ**：本育成／継承デッキの保存・切替、イベント設定、統合／比較、重複、所持・逆引き、目標セット、0〜4凸のヒント性能、検索、設定JSON入出力をF-01〜F-09で確認。公開Pages／実ブラウザ／Windows・Androidの各受け入れ条件を、人工テスト・実出典検証と分けて評価する。

**並行可能な作業**：UmaSim先行の[新カード検出・GitHub派生JSONの条件付き取得](derived-github-daily-pending-ledger-20261029.md)、キャッシュ・UIの保守、既存CI回帰。元JSON未掲載の新カードは持越保留し、旧563カードの照合・補修に割り込ませない。出典やユーザー判断に依存しない実装は進めてよいが、未解決のPhase 2残件を**完了したことにして**下流の正式公開を進めない。

**順序変更が必要な場合**は、[残件台帳](phase2-open-items.md)で未解決の項目、後続工程への影響、先行させる理由を明示し、ユーザーの確定判断と照合してからこの作業順を改定する。旧監査文書・GitHubの過去PRにある「次の作業」を、それだけで現在の指示にしない。A/B/Cの合格条件は[検証計画](verification-plan.md)を参照する。

### 汎用変換器から継続更新工程へ進むための先行ゲート

**旧GameTora HTML直接取得方式専用のゲート（2026-10-29保留）**。[4Aの履歴的な受け入れマトリクス](verification-plan.md#4a-gametora汎用取得変換器の次工程引き渡しゲート)は、将来直接取得を再開したときの参照資料として保持する。**派生GitHub JSONを入力とする製品開発には適用しない**。新しい派生JSON・イベント収録・アプリ配信の検証は[4B](verification-plan.md#4b-構造化github派生dbによる製品完成ゲート2026-10-29)を用いる。

**イベント開発の実行単位（2026-10-26更新）：** 未対応イベントをカードごとの個別プログラムではなく、固定GT全母数の原因別コホートで分類し、効果コード／分岐規則ごとの**共通変換器を一括適用**する。既存の検証A/B/Cは維持するが、1イベントごとに専用overlay・専用PRを増やさない。出典が曖昧な規則は同種全部を保留し、出典に明記されたまとまりから変換する。[全件コホートと最初のU.A.F.対応](phase2-gt-batch-cohort-uaf-20261026.md)。

**出典更新の運用ゲート**：構造化した第三者GitHub `systemless10/UmamusumePS` の固定コミット・Git blobと、UmaSimのカード／スキル辞書を基準に追加カードを検出・事前検査する。JSON未掲載カードは持越保留とし、期限経過だけでGameTora本体HTMLの自動取得へ切り替えない。固定出典の更新監視→単一レビューIssue→**メタデータのみの未採用Draft PR**を維持し、公開DBへの投入には独立したイベント内容と利用条件の審査が必要。特定イベントに疑義・欠損があれば、GameTora公式ページとGameWithの記載を**個別の編集確認資料**として用いられるが、サイトHTML汎用自動抽出の再開を先行条件としない。

**他Phaseへの依存**：Phase 1のカード／スキル辞書の独立照合、Phase 3〜5の機能・端末・公開運用は上記4工程に沿って進める。Phase 2の残件と同じ「現在の優先順位」をここで重複して列挙しない。カード・階層・特殊IDの曖昧さは根拠のある数値IDで扱い、旧2025年限定の名称を現行確定値として採用しない。物理端末未検証はLinux Chromiumの合格で代替しない。

**直接取得器は保留**。他機能の実装、派生JSON経由のイベント収録、増分更新、Pages検証を直接取得器の完成でブロックしない。ただし各工程の正確性・権利・公開承認は省略しない。対象範囲を縮めて完了宣言するには利用者の仕様決定が必要です。実データと数値の最新状況は [status.md](status.md) に記録します。
