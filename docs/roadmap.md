## 最終目標とスコープ

全対象サポートカードについて、本育成・継承育成のデッキを手動作成・比較し、**通常ヒント、イベントの選択肢／結果／後続分岐、スキル階層、重複、目標カバー**を確認できるWebアプリ。自動最適化・サポカ以外の経路・イベントの外部的な発生確率は対象外。詳細は [requirements.md](requirements.md)。

## 依存と当面の優先順

**最終運用は「新カードの差分追記」（2026-10-29利用者再確認）**：過去の全カードをGameToraで再取得・DB差し替えする計画ではない。以前と今の全サポカ名簿で追加IDを検出 → そのIDのGameTora元サイトだけ取得 → 情報を汎用変換 → 正しく変換できた新カードのイベントだけ既存DBへ追記 → 既存カード・ユーザー設定・承認証跡は変更しない。未掲載・部分抽出・元サイト取得失敗時は**当該新カードだけ**を保留台帳に残し、翌日以降に新規差分が消えても再試行。ほかの新カードが検証・承認済みなら個別に追記可能とする。重複追加の防止と各カードの追記時失敗における原子的な無変更を合格条件とする。

**2026-10-29実装進捗**：任意新カードIDのURLを元GameTora一覧の実在リンクに照合し、1回2カード以内で四系統の非公開結果候補へ投影する読み取り専用CLIを実装。元サイト実Chromeでこの新経路の検証、日次保留台帳の継続保存、完全な内部選択・分岐モデルと公開承認済み追記は**未完成**。詳細は[増分取込記録](new-card-event-incremental-intake-20261029.md)。

**当面の実装順序**：(1) 前後UmaSim名簿の新規ID差分判定と追加専用の既存DB結合・検証ゲート、(2) GameToraの任意の**新カード**の全表示イベントパネルを、カード個別の固定値なしにスキーマへ変換する共通アダプタ、(3) 変換済みカードだけを審査・配信ゲートを守って自動追記する継続更新ワークフロー。**既存DBへの全件置換は実施しない**。Phase 2の既存カード全件監査や固定GT比較は、過去の技術検証の補助資料として残すが、この機能の必要条件とはしない。

**現在の優先工程（2026-10-29再確認）：GameTora本体からの汎用イベント変換器を完成させる。** 元サイトに**表示された情報だけ**を入力とし、イベントパネル・表示上の選択肢候補・排他的結果・効果の種類／数値・スキルID／ヒントLv・直接付与・連続イベント内部で明示された停止／後続関係を、アプリの独自イベントモデルに共通変換する。結果の「成功／失敗」「大成功／成功」という**名称の区別はこの変換の対象外**。元サイトに表示がないなら中立的な「結果1／結果2」で扱い、**結果番号と獲得報酬の差だけは保持**する。

**この工程の検証・完了条件：** (1) 合成データで通常イベント・選択式・OR複数結果・ヒント・直接付与・打ち切り・後続依存の全パターンを機械検査、(2) 元GameToraの複数カードの表示結果を同一汎用器で解析し原サイトの記載漏れ・誤経路・未解析件数を監査、(3) Chromeで取得・変換・独自スキーマの検査まで実行。元サイトが実際に表示していない部分は「未記載／未抽出」を分けて報告し、別サイトから補わない。公開権利・本番導入は独立ゲート。この工程では**GameWith参照、攻略サイト間の差異調査、カード専用の結果名マッピング、実ゲームでの成功名称の確定を一切必須化しない**。補完・相違点の裁定は汎用変換ができた後に取り組む。

### 汎用変換器から継続更新工程へ進むための先行ゲート

**現在の優先順は「汎用取得・変換器の完成・検証 → 継続更新の接続」で固定する。** 前段のゲートが未通過である間は、保留台帳の永続保存、日次スケジューラ、承認後の原子コミットなど**後工程の新規実装を次の主作業に選ばない**。既に作成済みの安全な増分取込部品は維持してよいが、それらが存在することや2枚の実Chrome成功を理由に先へ進めない。先行工程に必要なテスト基盤・不具合修正・取得の安全対策は実施してよい。

前段を「完成」として引き渡すには、[専用の受け入れマトリクス](verification-plan.md#4a-gametora汎用取得変換器の次工程引き渡しゲート)の**A／B／Cを個別に通過**させる。最低限、事前選定した**構造の異なる複数カード**（新SSR2枚だけでは不可）について、GameToraの各表示パネル／グループ／結果／全ての表示効果／ヒントID・Lv／直接付与／明示された連続内部停止・依存を、**原サイト表示と独立に位置照合**する。サンプルに未解析の表示要素が残る場合や、結果位置が未確証の場合は**未通過**。サイトに元から表示されない情報は「元サイト未記載」として別に記録し、変換失敗から隠さない。カード固有の例外コードで合格件数を合わせず、元サイトの変更時には静かに誤変換せず拒否する。

**工程途中のPRマージと工程移行は別**：部分実装や試験コードをマージしてもよいが、PR・[最新状況](status.md)には「汎用変換器の引き渡しゲート未通過」と残す。ゲートの根拠を満たして初めて、後工程の継続更新の新規実装を優先する。公開・権利承認はさらに別のゲートであり、この引き渡しだけで公開可能にはならない。

**イベント開発の実行単位（2026-10-26更新）：** 未対応イベントをカードごとの個別プログラムではなく、固定GT全母数の原因別コホートで分類し、効果コード／分岐規則ごとの**共通変換器を一括適用**する。既存の検証A/B/Cは維持するが、1イベントごとに専用overlay・専用PRを増やさない。出典が曖昧な規則は同種全部を保留し、出典に明記されたまとまりから変換する。[全件コホートと最初のU.A.F.対応](phase2-gt-batch-cohort-uaf-20261026.md)。

**出典更新の運用ゲート**：新カードは派生GitHubデータだけの更新待機ではなく、一定の待機期間後に元GameTora公式サイトをカード単位で確認し、その詳細にも欠損が残る場合のみGameWithで補う（[現行手順](upstream-refresh-operations.md)）。公式サイトの事実・結果を自動採用したり原文を転載する更新ジョブはまだ未実装。既存の[継続更新手順](upstream-refresh-operations.md)の毎日日次元blob差分監視→単一レビューIssue→**メタデータだけの未採用Draft PR**を保守する。新規の実元候補に対する**全件の構造・カード・スキル辞書preflight**は実装済みだが、出典内容の内部報酬／GT↔UmaSim数値スキルIDの**意味と経路の独立裁定**は未自動化。残る工程は実候補の陽性ケースでのB全件実地確認と、人間が確認した固定ピン採用PRの作成。監視・候補Draftの成功を正式イベント公開やシナリオ対応の完了と扱わない。

1. **Phase 2・現行の独立IDと全件収録範囲を検証**。固定GameTora由来データの技術用スキル投影と、ゲーム実機の独立再現を必須条件にせず、採用元のGameTora固定版と例外裁定元GameWithの掲載事実を正とする。旧2025年マスター名でのみ対応したスキルIDと、GameTora側が元データを持たないカードについて、最新の独立出典と例外位置を検査する。[現在の母集団・出典と残件](status.md)。
2. **Phase 2・本番イベントの公開ゲートを整備**。イベント内部の結果・選択依存を維持した独自の日本語表示、元データと表現の再利用条件、出典の追跡、ユーザーが承認した公開イベント台帳を用意する。技術変換成功を一括で正式収録・公開承認済みに昇格しない。出典に明記された事実の採用に実ゲーム再実測を追加要求しない。[公開時の要件](checker-public-catalog.md)。
3. **Phase 1・カード／スキル辞書の独立照合**。カードと通常ヒント、ヒント性能、階層、特殊IDの独立検証を実施する。異IDの同名スキルを勝手に同一化せず、2025年限定の古い名称を現行の確定値に置かない。
4. **Phase 3～5・機構／母集団／受け入れの分離試験**。GitHub Pagesでのブラウザ試験に加え、採用元に明記された内部報酬分岐・Windows／AndroidでのWebアプリの表示／操作を別々に確認する。発生確率等の外部条件と、内部連続分岐・打ち切りを混同しない。

**一般の独立した機能は並行開発してよいが、上記のGameTora汎用変換器→継続更新の依存には先行ゲートを適用する。** 他工程の成果やCI通過を前段の完成と見なさない。対象範囲を縮めて完了宣言するには利用者の仕様決定が必要です。実データと数値の最新状況は [status.md](status.md) に記録します。
