# 既存GameTora変換結果と元サイトの差分再現（2026-10-28）

## 検証の目的

ユーザーの指摘を受け、**先にSSR30322／30323など未収録新カードを個別調査するのでなく、既にGameTora派生GitHubデータからウマサルタントの非公開イベント候補へ変換したカードを、GameTora本体から同じように再現できるか**を比較する工程へ切り替えた。最初の対象は固定版に存在するSSR30001（スペシャルウィーク）。

この試験の「比較基準」は**元の派生JSONそのものではなく**、`poc/src/gametora_whole_event_normalize.cjs::transformDocument` がそのJSONを実際に変換した結果である。これは既存の数値・分岐**中間候補**であって、最終的にPagesへ公開する `reviewed_events.v1.json` の完成データとは異なる。両者の関係をすり替えない。

## 入力と実行手順

- 基準となる既存データ：`systemless10/UmamusumePS` の固定コミット `6e38b54af4fad397ff4491e63007a90705a4fe67`、`server/data/events/gametora/support_30001.json`、固定Git blob `6aca60590854f402a67da82c2ffa7295e564b40f`。CIの一時領域だけで取得。
- 元サイト： [GameTora本体のSSR30001](https://gametora.com/ja/umamusume/supports/30001-special-week) を通常のGitHub Actions Chromeで表示。非公開・固定1カードを対象とし、5つのイベント開閉パネルを読んだ。
- スキルID：UmaSim `skill_data.txt` 固定Git blob `0c6ea6d72b037b24ee40860f73b0e86db47aab1d`。元サイトのスキル名を独立した数値IDに一意照合してから比較。
- 方法：旧出典から**同じ変換器で**5イベントを正規化。元サイト側ではイベント名を既存の一意照合で元位置と結び、各経路の数値効果種別・符号付き増減・数値スキルID・ヒントLvを別々に読み込んだ。経路候補が**多重集合の一意割当**にならない場合は合格しない。選択肢の日本語文章、HTML、画像、元イベント本文はリポジトリ・CIログへ持ち出さない。

コード：[既存変換済み候補との照合器](../poc/src/official_gametora_existing_normalized_parity.cjs)、[実Chromeでの比較](../poc/tools/probe_official_gametora_browser.cjs)、[合成・異常系試験](../poc/tests/official_gametora_existing_normalized_parity.test.cjs)。

## 2026-10-28の実測（固定1カード）

| 観測指標 | 実測 | 判定 |
| --- | ---: | --- |
| 旧固定からの正規化イベント数 | 5 | 分母確定 |
| 旧固定から正規化した経路 | 9 | 分母確定 |
| 元サイト表示から一意に数値割当できた経路 | **9/9** | 部分的成功 |
| 既存正規化結果との照合で、解析対象の全数値が分類できたイベント | **1/5** | 不完全 |
| 元サイトの符号付き数値のうち型不明な文字片 | **8件** | 未分類 |
| 型不明の理由 | 8件とも**認識可能な効果名が元テキスト断片に存在しない** | 要取得方法改善 |
| 原サイトの選択肢・確率結果のゲーム内意味 | 未確認 | 本番変換未完成 |
| イベント内の後続依存・打ち切り・全ての非スキル報酬 | 未確認 | 本番変換未完成 |

一致した9経路は、**既存変換器が数値等を読み取れる範囲での一意対応**を意味する。未分類8行を無視した**全効果の一致**を意味しない。選択式イベントと自動イベントの意味、絆の受け手、発生確率、文章、元ゲーム内の到達条件も別に検証が必要である。

数値解析器の診断では、8件とも「複数の効果種別が競合している」のではなく、そもそも数値片の文字列に効果種別を指す文字がないことを確認した。近傍の親DOM要素に**同じ符号付き数字を1つだけ含む一意な効果名**がある場合に限り補完できる安全策も実装したが、このカードでは該当する親文脈を得られず、自動的な型付与は行っていない。次工程ではこの8件の**DOM構造上の実際のラベル位置やアイコン構造**を確認する。既存変換結果を用いてサイトの不足効果種別を逆算・捏造しない。

## A・B・Cの合格境界

- **A 機構**：合成5イベントの既存変換器からの照合、異なるID/Lv、OR分岐漏れ、同署名重複、未解釈効果、出典イベントとの誤結合を拒否。結果が合致してもスキーマ公開フラグはfalse。
- **B データ**：母集団は既存SSR30001の5イベント9経路に限る。経路の一意対応は9/9、厳密な型付けは1/5と明記。既存559件等の派生全カードや、現行ゲームの全収録網羅性を保証しない。
- **C 元サイト実ブラウザ**：GitHub Actions Ubuntu 24.04のChromeで旧1枚を開いた実測。**物理端末や実ゲーム中のイベント再現ではない**。
- **D 公開**：新しい公開イベントは0件。元コンテンツの転載許可、一般的な大量取得方法・最新ゲームとの一致、全アプリ形式への一括変換は引き続き別ゲート。

## 2026-10-28追加実証：元サイトの「友情ゲージ」を絆数値として取得

初回PR #247の調査では、元サイトに符号付き数値が**8件残り**、従来パーサが効果種別を識別できなかった。これは単にDOMから名称を取れていないわけではなく、**元サイトの同一テキスト要素内で、パーサの既知語`絆`とは別に`友情ゲージ`と記述される**ためだった。

診断段階（[PR #248](https://github.com/Nimrodx0/Umasupport/pull/248) のActions実ブラウザ）では、8件全ての元テキスト片が「友情」「ゲージ」の両字句を含み、画像やSVGのラベルを推測する必要はないと判明。旧固定GitHub由来データを元変換器で正規化すると、対応カードには絆ゲージの数値効果が8件あるが、**この一致は語彙を推定するための参考にとどめ、元サイトに実際に表示された`友情ゲージ`を効果種別の直接根拠として採用**した。特定カード専用のDOM座標や旧JSON由来の暗黙穴埋めは実装しない。

抽出器 `official_gametora_numeric_fact_parser.cjs` の`bond`語彙に`友情ゲージ`を追加。既存 `official_gametora_existing_normalized_parity.cjs` の比較対象にも`bond`の符号付き数値を加え、別々に元サイトと既存変換済み候補の8件を照合した。修正後のChrome観測は以下のとおり。

| 旧固定イベント番号 | 数値経路の一致 | GameTora表示内の「友情ゲージ」 | 旧固定を独自変換した`bond` |
| ---: | --- | ---: | ---: |
| 1 | 一致 | 2 | 2 |
| 2 | 一致 | 2 | 2 |
| 3 | 一致 | 0 | 0 |
| 4 | 一致 | 2 | 2 |
| 5 | 一致 | 2 | 2 |
| **計** | **9/9経路** | **8件** | **8件** |

**最終実測**：数値種別・値とヒントID/Lvを含む**5/5イベント・9/9経路の対応が一意**になり、元サイトで識別不能な符号付き数値片は**0件**。これは前節の**初回実測1/5と8件未分類を解消した追加実測**であり、初回値が当時の測定として誤りだったという意味ではない。旧経路プローブは絆を比較対象から除外する役割を明確にし、**既存変換結果との新しい完全な数値比較器では絆8件も厳格に比較**している。

留保：絆効果が**どの人物／対象に付与されるか**、画像や選択肢文章、連続イベントの到達条件、公式ゲームでの結果確率は今回の数値等価性に含まれない。アプリ用正式JSONの全フィールド等価性と、公開の権利・承認は未完了。出典が変われば、何も確認せず旧形式へ自動昇格せず、CIで5件／9経路／8件の構造差分を検出する。

## 今後の順序

1. SSR30001の未分類8数値片が、GameTora本体DOMのどの要素から効果種別を取得できるかを**構造的に**確認する。ラベルと数値が分離した表示構造なら、元サイトの抽出器に汎用規則を追加する。
2. その後、SSR30001について既存正規化済み5イベントの**全経路・全対象効果**を比較できるところまで進める。イベントの型・連続依存・結果の意味も別途チェックする。
3. 既存変換済みDBから、数値構造・OR・条件付き結果・打ち切りなどの**原因別に古いカードを機械選定**して比較対象を広げる。新カードの個別実装は優先しない。
4. 既存**数値中間候補**だけでなく、その先の**ウマサルタントのアプリ用イベントJSON投影**ともフィールドごとに比較し、公開ゲートとは独立して等価性を確認する。

## サイトアクセス運用

PR CIでは**既存SSR30001のみWebサイトへアクセス**し、新SSR2枚を繰り返し照合するジョブと3カードの初期HTML検査は`workflow_dispatch`（明示的な手動起動）の場合だけ実行する。これにより新サポカをテストの常時分母に使わない。出典の権利・利用条件を確認せず大規模クロールはしない。
