# 全サポカ向けイベントデータ供給元の選定（暫定調査：2026-10-16）

**【2026-10-21以降は供給元の選定履歴】** この2026-10-16時点の候補比較表と当時の優先度は、現行の入力優先順位ではありません。採用済み方針は [GameTora由来データを基準／GameWithは疑義の裁定](gametora-baseline-event-policy-20261021.md)。古い母集団・評価は当時の測定として参照してください。

## 開発順序の変更

全サポカを扱うアプリである以上、先に**広範囲かつ持続的にイベントデータを得られるソース**を選び、収録状況を数値化する。45枚の部分データに合わせた実イベント実装を先行するのは非効率。Issue #2 の「実データ導入」は、供給元の選定ゲートが通るまで保留する。

基準となる集合は、現行アプリのUmaSim `support_card.txt` にある **563件の異なるサポカID**。これは2026-10-16時点のアプリの比較用分母であり、ゲームで実装済みの全カード枚数を保証するものではない。

## ソース選定の実地検証

1. 最優先の大規模JSONを**第三者データをリポジトリへ同梱せずに**ローカルまたは読み取り専用環境で解析し、カード／イベント／選択肢／報酬の件数とルート表現を確定する。
2. カード名・ゲーム内IDの紐付け方式を調べ、UmaSim側の563カードIDと突合する。自動名寄せと実ID直結は区別し、同名・別レアリティの誤対応を拒否する。
3. 563枚のうち**データあり・明示的にイベントなし・未収録・照合不能**を区別し、カード別イベント件数・選択肢数・スキル報酬数を出す。ゲーム内の実イベント数が不明なら「真の網羅率」ではなく「対象カードのレコード有無率」と呼ぶ。
4. 連続イベントの親子関係、先行選択肢、打ち切り、成功／失敗、任意イベントがデータとして明示されているかを数値化する。曖昧なものは推測で自動集計しない。
5. 更新頻度・停止リスク・配信量・CORS・無制限GETの負荷・権利者と情報転載元の利用条件を確認する。公開リポジトリだから再利用が許可されるとは限らない。
6. 有力ソースが不足する場合、**イベント／選択肢／報酬は網羅的ソース＋ゲームマスター由来のID・連続段階**など複数ソースを補完的に使う設計を検討する。1つの不完全なJSONに最適化しない。
7. このゲートが通ってから、既存の `event_schema.js` と `event_review_compiler.js` へ実データをつなぎ、少数カードで検証して全件へ展開する。

再現可能な監査コード：`poc/src/cruise_source_audit.js`、`poc/tools/audit_cruise_source.cjs`。単体テストは `poc/tests/cruise_source_audit.test.cjs`。GitHub Actionsの **Event Source Coverage Audit** を手動実行できる。自動定期取得は設けない。

## 2026-10-16 採用された公開方式

公開アプリのイベント配信は外部サイトへのブラウザ直Fetchではなく、ウマサルタント独自の公開JSONとする。初期入力候補UmaUmaChecker、欠損・新規だけGameWith個別記事で確認。U-toolsは当面使わない。ソースデータの利用条件、正式ID・連続・打ち切り・結果条件を確認しないまま候補を獲得可能イベントとして自動追加しない。詳細：[実装・公開手順](checker-public-catalog.md)。

## 2026-10-17：U-tools個別ページの限定的な照合（PR #48）

[SSR30241調査](utools-third-source-event-audit.md)。公開ページを閲覧するとイベント見出しは連続5＋ランダム13＝**18件**で、2025年masterカード直結18件と数が同じだが、Checker 2026年固定版は17件。**件数一致だけでIDが一致するとは断定しない。** U-toolsのアクセス権限・元データの独立性・最終更新日は未確認。GitHub Actionsからの単発HTML GETはHTTP 403で拒否されたため、保護の回避はせず自動GETを削除。見出しの3者名称照合は**未実施**で、830241004が第三サイトにあるかも不明。ローカル手動入力の照合器と人工HTMLテストだけ用意しておく。従来の「U-toolsは当面イベントの公開データ入力元として使わない」という方針は維持。
