# 全サポカ向けイベントデータ供給元の選定（暫定調査：2026-10-16）

## 開発順序の変更

全サポカを扱うアプリである以上、先に**広範囲かつ持続的にイベントデータを得られるソース**を選び、収録状況を数値化する。45枚の部分データに合わせた実イベント実装を先行するのは非効率。Issue #2 の「実データ導入」は、供給元の選定ゲートが通るまで保留する。

基準となる集合は、現行アプリのUmaSim `support_card.txt` にある **563件の異なるサポカID**。これは2026-10-16時点のアプリの比較用分母であり、ゲームで実装済みの全カード枚数を保証するものではない。

**重要：** ファイルサイズ、レコード数、更新日時は「全サポカの全イベントが網羅された」ことの証明ではない。未解析のソースについて網羅率を推測で記載しない。

## ソース選定の実地検証

1. 最優先の大規模JSONを**第三者データをリポジトリへ同梱せずに**ローカルまたは読み取り専用環境で解析し、カード／イベント／選択肢／報酬の件数とルート表現を確定する。
2. カード名・ゲーム内IDの紐付け方式を調べ、UmaSim側の563カードIDと突合する。自動名寄せと実ID直結は区別し、同名・別レアリティの誤対応を拒否する。
3. 563枚のうち**データあり・明示的にイベントなし・未収録・照合不能**を区別し、カード別イベント件数・選択肢数・スキル報酬数を出す。ゲーム内の実イベント数が不明なら「真の網羅率」ではなく「対象カードのレコード有無率」と呼ぶ。
4. 連続イベントの親子関係、先行選択肢、打ち切り、成功／失敗、任意イベントがデータとして明示されているかを数値化する。曖昧なものは推測で自動集計しない。
5. 更新頻度・停止リスク・配信量・CORS・無制限GETの負荷・権利者と情報転載元の利用条件を確認する。公開リポジトリだから再利用が許可されるとは限らない。
6. 有力ソースが不足する場合、**イベント／選択肢／報酬は網羅的ソース＋ゲームマスター由来のID・連続段階**など複数ソースを補完的に使う設計を検討する。1つの不完全なJSONに最適化しない。
7. このゲートが通ってから、既存の `event_schema.js` と `event_review_compiler.js` へ実データをつなぎ、少数カードで検証して全件へ展開する。

## 2026-10-16時点の結論

**採用する主データ元はまだ決まっていない。** まず `umaumacruise_customjson` の大規模JSONを実際に集計し、カード単位の収録率と選択肢報酬の表現可能性を確かめる。ウマ娘Wikiのマスター由来連続情報を検証用の第二候補とする。

以降は、データソース評価をIssue #2の**最優先**とし、個別カードのレビュー・公開版イベント集計の導入を保留する。既存のイベントスキーマ・人工データテストは維持する。
