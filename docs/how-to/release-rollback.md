# 公開版のロールバック・復旧手順（W5.3）

## 原則

障害発生時も現行mainや公開イベントの無条件巻戻し、履歴のforce push、利用者の保存データ消去を行わない。候補を隔離した環境で確認し、緊急修正または明示承認された復旧PRを選ぶ。現行データと旧ランタイムの組合せは自動的に安全とはみなさない。

## 非破壊の予行

[W5専用CI](../../.github/workflows/w5-rollback-rehearsal.yml)はD065の公開受入済み固定コミット `441046b7e2d2247c1c8ea534e9bf0b1f3ef9edd0` を一時展開し、旧2,487イベントのbyte SHAを確認する。固定UmaSim辞書・同一ローカルorigin・Chromiumコンテキストを使い、現行辞書を維持したアプリ単独の巻戻しと、旧固定UmaSim（f6e4501）も組み合わせる複合障害を分けて予行する。1280/390pxの両方で次の境界を確認する。

- 既存設定を読み、旧版の通常操作で新しい育成条件を落とさない。
- 旧固定辞書にも戻した場合に存在しない目標IDを含む設定は明示エラーで停止し、保存bytesを消去しない。
- 現行版への復帰後に設定・イベント・育成条件を復元できる。
- 元辞書の本文は一時メモリのみ。実利用者設定・本番Pagesは変更しない。

## 実障害時の判断・操作

1. 公開受入の失敗箇所、期待コミット、実配信の版識別子・資産SHAを記録する。データソース停止とアプリ配信破損を区別。
2. 最終受入済み版のコミットと現行変更範囲を照合し、ロールバックで失われるイベント・ID・設定互換性を事前に確認。現行承認台帳と異なる公開集合への変更は別審査。
3. 原則は不具合箇所だけを修正するPR。旧ランタイム復旧が必要なら新しい版識別子を発行し、通常入口・HTML・全資産の版を同期する。保存領域の消去を回避し、不適合目標があれば復帰まで保存設定を保持する。
4. Core、公開承認ゲート、固定研究（変更範囲に応じて）、専用ロールバック予行を確認してからmainへ統合。公開先の通常入口、配信JSON、資産SHA、設定・キャッシュ復帰を確認する。
5. 復旧内容・確認時刻・未検証を[status](../project/status.md)とIssueに記録。物理端末受入は既存方針で保留。

予行の成功は本番ロールバックの実施・物理端末受入を意味しない。固定旧版が将来の全設定に互換という保証でもない。
