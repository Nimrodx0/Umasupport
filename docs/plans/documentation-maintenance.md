# D：文書品質の継続改善計画

[詳細計画](index.md) ／ [文書運用規約](../governance/documentation-policy.md) ／ [改善受付 Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)

**目的**：Umasupportの開発者・AIエージェントが現行の契約と検証根拠を少ない探索で確実に見つけられるよう、**実際の開発で起きた不便・誤参照・手戻りを継続的に改善**する。製品開発WトラックやP0～P5の研究内容は別管理。文書のフォルダ移動それ自体を成果指標にしない。

## 運用方法

- **発見の入口**：開発中に観測した文書の問題・改善可能性は[継続受付Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)へ。D番号付き小工程へ整理し、優先度と再現条件を付ける。感想や推測は実測と区別する。
- **正本**：このファイルには未完の作業・現在の判定・採用ゲートを簡潔に記載。時点付きの大きな監査は `docs/evidence/quality/`、恒久的な文書方針は[governance](../governance/documentation-policy.md)へ置く。PR別の経緯はGit履歴とIssueへ。
- **更新契機**：開発タスクの開始・終了時に、必要文書へ到達できたかと旧リンク混在の有無をチェック。新たな障害が実際に発生した場合にD項目を追加し、存在しない問題を作らない。改善を実行したら再現→対処→同じ検査で確認する。
- **採用指標**：①正本までの探索手順／失敗、②古い指示・旧パスの誤認、③文書とコード/実行ゲートの矛盾、④リンク/アンカー切れ、⑤複数正本の同期負担。検索時間やトークンの改善を測っていないときに改善したと断言しない。
- **制約**：原本を削除せず、実測と仮説、採用済みと未採用を分離。フォルダの過剰な細分化・大規模移動をデフォルト解決策にしない。[文書更新手順](../how-to/update-docs.md)に従って検査する。

## 受付・完了の条件

不都合ごとに **D番号、発見日、作業名、失敗例または再現手順、影響、改善案、優先度、状態、Issue/PR/CI、検証結果**をIssue #388へ追加する。

個別改善の完了は、正本への到達とコード・文書・検証の整合を対象PRのCIまたは再現可能な手順で確認し、旧原本と判断理由を保持した時点とする。**ファイル増加やフォルダ再編だけでは完了ではない。**

**現状**：独立運用の仕組みと初回の実開発上の障害を記録。D.1のPR統合やD.3の発見性測定は未実施。
