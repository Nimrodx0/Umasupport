# D：文書構成の継続改善計画

[上位の位置づけ](../project/roadmap.md) ／ [詳細計画](index.md) ／ [文書運用規約](../governance/documentation-policy.md) ／ [横断的な改善候補 Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)

**対象は、複数の文書領域・開発工程にまたがる構造的な問題だけ。** 普段の開発で発見した個別のリンク不備、パスの更新漏れ、誤った説明、単発の不整合は**発見時にその作業のPRで修正**する。修正を先延ばしにするために記録する仕組みではない。

## 目的・判断原則

- **一括改善が合理的な場合にだけ蓄積**：正本配置、領域間の役割分担、AGENTSからの探索導線、文書更新手順、自動検証の体系など、複数領域を同時に改める必要がある課題を記録して、関連項目をまとめた改修PRで実行する。
- **発見時に修正する問題**：孤立リンクや旧パスの参照、研究PRの新mainへの移行、個別文書の重複・矛盾、単一CIの修復などは、その場で修正・検証する。横断的な根本原因が判明した場合に限り追加でDへ記録する。
- **改善の正本**：ここには横断課題の理由・範囲・優先順位・採用ゲートのみ。実例・議論は[Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)、採用後の恒久ルールは[文書運用規約](../governance/documentation-policy.md)。研究データや製品の工程はP／Wの正本を変更する。
- **バッチ化の基準**：文書種別や正本の責任範囲が変更される、3つ以上の独立した参照経路やCIに影響する、複数の例で同じ根本原因が再発する、などの証拠がある場合。件数は機械的な必須条件ではなく、**一緒に直すことで全体整合性が高まり手戻りが減るか**で判定する。
- **実施・終了**：対象の現行正本と旧原本の内容保存、リンクと見出し・判定台帳・CI参照・実コードの整合を確認してから改修。効果は実タスクの探索と手戻りで測り、リンクが通っただけで改善成功と断定しない。

## 横断的な改善候補

| ID | 改善したい構造上のこと | 状態 | まとめて改修する判断条件 |
| --- | --- | --- | --- |
| D.1 | AIエージェントが文書から現行の正本・検証・過去の証拠を**短い経路で正しく探せるか**を実作業で検証する | 観測・方法検討 | P2と製品の別種タスクで複数の探索失敗・正本誤認が観測されたら、導線・索引・運用手順・検査をまとめて見直す。比較可能な実測値がない現時点で性能向上を主張しない。 |
| D.2 | 文書の増加に伴う**正本の二重化・索引陳腐化・参照方法の繰り返しの手戻り**を防ぐ | 事例蓄積待ち | 複数領域で同じ根本原因が確認された場合にだけ、基準・自動検査・更新フローを一括改修。単発事例は元PRで即時修正する。 |

## 現在の個別修正との境界

- **研究PR #380～#383が旧文書パスを持つ問題**は、[PR #384](https://github.com/Nimrodx0/Umasupport/pull/384)後に実際に発生した**個別の移行・統合問題**。研究を失わない形で修正する必要があるが、上表に「改善提案」として積み上げて放置する案件ではない。具体的な作業・CIは該当研究PRか移植PRで追跡する。
- **Dトラックの索引不足**も、発見したこのPRで[project/README](../project/README.md)、[ロードマップ](../project/roadmap.md)、[plans入口](index.md)、[docs入口](../index.md)を修正する。改修を将来の一括整理へ持ち越さない。

**この計画は製品の新機能・P2モデル発動率・サポカ評価を新たに承認するものではない。**
