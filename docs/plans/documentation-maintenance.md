# D：文書構成の継続改善計画

[上位の位置づけ](../project/roadmap.md) ／ [詳細計画](index.md) ／ [文書運用規約](../governance/documentation-policy.md) ／ [横断的な改善候補 Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)

**対象は、複数の文書領域・開発工程にまたがる構造的な問題だけ。** 普段の開発で発見した個別のリンク不備、パスの更新漏れ、誤った説明、単発の不整合は**発見時にその作業のPRで修正**する。修正を先延ばしにするために記録する仕組みではない。

## 目的・判断原則

- **一括改善が合理的な場合にだけ蓄積**：正本配置、領域間の役割分担、AGENTSからの探索導線、文書更新手順、自動検証の体系など、複数領域を同時に改める必要がある課題を記録して、関連項目をまとめた改修PRで実行する。
- **発見時に修正する問題**：孤立リンクや旧パスの参照、研究PRの新mainへの移行、個別文書の重複・矛盾、単一CIの修復などは、その場で修正・検証する。横断的な根本原因が判明した場合に限り追加でDへ記録する。
- **改善の正本**：ここには横断課題の理由・範囲・優先順位・採用ゲートのみ。実例・議論は[Issue #388](https://github.com/Nimrodx0/Umasupport/issues/388)、採用後の恒久ルールは[文書運用規約](../governance/documentation-policy.md)。研究データや製品の工程はP／Wの正本を変更する。
- **バッチ化の基準**：文書種別や正本の責任範囲が変更される、3つ以上の独立した参照経路やCIに影響する、複数の例で同じ根本原因が再発する、などの証拠がある場合。件数は機械的な必須条件ではなく、**一緒に直すことで全体整合性が高まり手戻りが減るか**で判定する。
- **実施・終了**：対象の現行正本と旧原本の内容保存、リンクと見出し・判定台帳・CI参照・実コードの整合を確認してから改修。効果は実タスクの探索と手戻りで測り、リンクが通っただけで改善成功と断定しない。

## 横断的な改善候補

| ID | 改善したい構造上のこと | 状態 | まとめて改修する判断条件 |
| --- | --- | --- | --- |
| D.1 | AIエージェントが文書から現行の正本・検証・過去の証拠を**短い経路で正しく探せるか**を実作業で検証する | 観測・方法検討 | P2と製品の別種タスクで複数の探索失敗・正本誤認が観測されたら、導線・索引・運用手順・検査をまとめて見直す。比較可能な実測値がない現時点で性能向上を主張しない。 |

| D.3 | **分野をまたぐ専門用語の優先名称・定義の正本を確立し、表記揺れと概念混同を防ぐ** | **初期運用を追加・全領域の棚卸しと移行は未完** | [用語・定義の正本](../reference/terminology.md)を共通入口とする。研究P2の「仮の最小差幅」のような曖昧な表現、同一概念の別名、異なる指標の混同などを根拠に、用語ごとに既存の現行定義を調査し、共通定義を登録／分野固有定義の正本にリンクする。繰り返される表記揺れや横断更新漏れが確認されたら、範囲を定めた移行・検査を一括実施する。未検証の旧研究記録やコード名を一律に置換しない。 |

## D.3：用語の正本と横断的な表記管理

**本作業の既知の欠落**：従来の文書運用規約は「現行の定義は`reference/`」と定めていたが、**用語の優先表記、定義の所在と分野間の同義語・異義語を探す共通入口がなかった**。P2.30の「仮の最小差幅」は、モデルの「脚質間の条件成立機会の差の最小下限」と試験用の「判定用閾値」を区別できず、利用者の理解を妨げた事例である。

**今すぐ行うこと**：承認された[全エージェント共通の命名・定義原則](../../AGENTS.md#専門用語の命名定義一貫性)を`AGENTS.md`に追加し、[用語・定義の正本](../reference/terminology.md)を設け、[文書運用規約](../governance/documentation-policy.md)・[更新手順](../how-to/update-docs.md)・[リファレンス入口](../reference/index.md)をつなぐ。既存の正確な技術定義を無断で重複作成しない。

**以後の横断課題と終了条件**：

1. P／W／Dの**複数領域で実際に再利用される用語**から対象を選定し、既存の正本・コード・テストを照合して、推奨表記・定義・略称・旧称・単位・適用範囲・採用状態を確認する。
2. 正本がないものは`docs/reference/terminology.md`で定義し、既存の仕様書に正本があるものは共通索引から参照する。同じ用語の競合した定義を複数正本として残さず、既存原文・固定研究報告は履歴として保持する。
3. 名称・定義変更で影響する**現行**文書、UI文言、図表、コードコメント・テストを限定的に修正する。別概念は同じ優先用語に押し込まない。ユーザーに対して初出説明をリンクだけで省略しない。
4. 関連する文書から正本へ到達できること、代表的な重要用語の定義と表示が一致すること、変更後の対象テストが通ることを確認する。**全用語の網羅率・機械的表記統一の完成は現在未達**。単純な表記誤りは発見したPRで修正する。

**このD.3は**文書の横断構造を整備する工程であり、研究P2で未承認の閾値・発動確率を確定する工程ではない。

## 現在の個別修正との境界

- **旧研究PR #380～#383の参照パス不整合**は個別の移行作業として[PR #391](https://github.com/Nimrodx0/Umasupport/pull/391)へコード・研究原本を現行配置で移植し、固定実験・アプリテスト・リンク検証が合格。旧4PRは二重マージ回避のため未マージでクローズした。**PR #391自体は未マージ**。横断改善の候補として保留せず、この個別PRで完了まで追う。
- **Dトラックの索引不足**も、発見したこのPRで[project/README](../project/README.md)、[ロードマップ](../project/roadmap.md)、[plans入口](index.md)、[docs入口](../index.md)を修正する。改修を将来の一括整理へ持ち越さない。

**この計画は製品の新機能・P2モデル発動率・サポカ評価を新たに承認するものではない。**
