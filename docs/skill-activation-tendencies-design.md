## 目的・非目的

- サポートカードが提供する**通常ヒント／承認済みイベント報酬**のスキルについて、ゲーム内の明示条件と実質的な発動傾向を解析し、距離・脚質・馬場・レース状況の観点からカード間で比較・検索する。
- カード一覧では少数の傾向ラベルを控えめに表示し、詳しい条件・証拠と例外は展開して確認できるようにする。
- **非目的**：特定レースの勝率・発動確率の断定、自動最適編成、実ゲームの条件再現の完全保証、未出典スキルへの効果捏造、イベント外部発生確率の推測。

## P2で合意した推論の手順と検討範囲（2026-11-04）

ユーザーと次の処理順序に合意した。P2の分類を検討するときはこの順序を逆転させない。

1. **条件単体の意味**：たとえば `order_rate <= 40` を「上位40%以内」、`phase == 1` を「レース中盤」と、別々の情報として解析する。順位割合条件単体が前方を要求するのであり、「中盤＋順位割合」の組が初めて前方条件になるわけではない。
2. **論理式・時期・状況の組合せ**：「中盤 AND 上位40%以内」は「レース中盤という時点で前方を維持」を要求する。`is_overtake`、競り合い、先頭維持など他の条件が増えれば、単独条件の適性評価をそのまま足したり優先したりしない。ORで複数経路があるときも、各経路を独立に評価する。
3. **ゲームシステムとの照合による脚質適性推定**：レース区間ごとの位置取りや脚質ごとの順位変動・追い抜き機会などを独立に確認し、発動条件を満たしやすい脚質を**推定**。出走頭数や同脚質人数・レース展開による例外を残す。**ゲーム内の厳格な脚質指定と推定を混同しない。**

**推論の前提**：順位・順位割合・追い抜き等をUmaSimのシミュレーションが無視・近似する場合がある。ゲームに存在する元条件とシミュレーターの判定結果を混同しない。脚質適性を断定する前に具体的なスキルの代表例と反例を提示し、利用者と判断基準を合意する。

**対象を予断で4分類しない**：「中盤前方／中盤後方／終盤前方／終盤後方」は説明用の例に過ぎず、P2の全体分類体系ではない。全125条件コードをまず意味と利用頻度・組合せで整理する。前後・中終盤以外の序盤、終盤迫る局面、ラストスパート、コース・坂・他馬との相互作用を初期段階で捨てない。

### 発動効果の有効性（別軸、検討保留）

発動条件が満たしやすいことと、発動した結果の速度・加速・回復等がその脚質とレース展開でどの程度役立つかは別問題。**後者も重要であり、将来の評価対象から除外しない**。ただしP2では発動条件の意味と成立しやすさを中心にし、効果の有効性については当面ユーザーに判断を委ねてもよい。元辞書の効果・発動位置・脚質ごとの差が、簡潔で誤解のない指標にできそうか実データの検討で判断し、必要ならユーザーと追加合意する。いまの段階で自動的な効果有効性スコアを実装しない。

## P2定性推定v2：終盤の追い上げによる適性の重なり（2026-11-05、後続判断で撤回）

2026-11-04の53件レビューでユーザーから、**意気込み十分のように終盤前半の後半までランダム発動地点が含まれる前方50%条件は、差し・追込にも十分に適性がある**と指摘された。参考：[猫炭「ウマ娘のレース展開を理解する」](https://note.com/sumi_wingedcat/n/n995257cc0c91)。記事は作戦ごとの区間別速度補正、終盤からの追い上げを説明するが、脚質別の順位分布と実際の発動率を測定した資料ではない。

- `phase_firsthalf_random == 2` は終盤前半のさらに前半（距離全体約66.7～75%）でランダム発動。順位割合50%以内なら**逃げ・先行寄り**を維持する。
- `phase_random == 2` は終盤前半全体（約66.7～83.3%）からランダム発動。順位割合50%以内なら**逃げ・先行／差し・追込も適性**として、主な前方脚質と追加で対象に含める後方脚質を別属性で保持する。
- 適性に含めた脚質すべての発動確率が等しいとの意味ではない。順位割合の元コード`order_rate <= 50`は変えない。発動タイミングの広さを**脚質固定の厳格条件**や**スキル効果の実用性**に読み替えない。
- 追加規則の適用条件：ランダム抽選窓がレース全体の75%地点を超える終盤の後半側にまで及ぶ**前方半数条件**。`phase == 2`のような局面成立判定だけでは「後半までランダム発動する」ことが保証されないので自動拡張しない。直線・コーナー依存・OR分岐混在・他馬条件は従来どおり別途解釈する。

この75%地点は終盤前半を2分する**ソース上の境界**を採用した初版の定性的ヒューリスティックであり、実験で最適化された閾値ではない。スキルが個々のレースでいつ発動するか、順位成立率は別途検証対象である。

## P2定性推定v3：順位方向を基本傾向、追い上げは時期の解釈として区別（2026-11-05、現行）

[発動窓による再評価と出典限界](skill-style-late-window-audit-20261105.md)に基づき、**「全距離75%を超えるランダム発動窓」から四脚質の適性を確定するv2規則は撤回**。これはウマ娘の脚質間の発動確率を直接測った結果ではなく、ゲーム仕様の区間境界を適性の境界と取り違えたため。

- 前方半数条件は暫定的に**逃げ・先行寄り**、後方半数条件は暫定的に**差し・追込寄り**を基本傾向とする。これは「他脚質では発動しない」という意味でも、脚質間の実発動率の差を測定した意味でもない。
- 局面・ランダム発動範囲・前半／後半等は元の条件式から**開始率と終了率を数値のまま別保持**する。発動窓が遅い地点にも及ぶ場合、後方脚質が追い上げて前方条件を満たしうる余地が増すことを注記するが、その地点で脚質間の優位が逆転するという新規ラベルは出さない。
- 意気込み十分（終盤前半全体からランダム）とハイボルテージ（終盤前半の前半でランダム）は、ともに基本は逃げ・先行寄り。発動区間は明確に異なるため、判断したい利用者にはそれを提示する。後方半数条件の上昇気流は差し・追込寄りを維持。
- 位置取りの変化は距離・脚質人数・速度スキル・コース・他馬との関係で変わるため、**固定のゲーム進行率で脚質適性を広げる／逆転させるルールは、順位分布の実測や再現能力の確認ができるまで導入しない**。

## P2の次の候補：複数頭の走行位置から順位条件成立頻度を測る（2026-11-05）

速度・進行距離の曲線から、**同一時刻**で各脚質の順位を比較する実験を進める。直接の先行候補は、固定GlobalSim v77の複数頭リプレイ位置データ。[位置分布パイロット](skill-position-probability-simulation-pilot-20261105.md)で9頭・同等ステータス・複数脚質編成を先に試す。公開者の多数の公式記録との照合結果はグローバル版の検証であり、日本版への同等精度の外挿を許さない。

`order_rate<=50`／`>50`の各局面におけるモデル上の成立頻度は**レースの位置取りに関する参考量**。同じウマ娘・ステータス・能力の実ゲーム内順位分布の確率でも、スキルの抽選確率や最終的な発動率でもない。実モデルでの大規模試行と日本版との独立照合が揃うまで**現行の53件の推定ルールに自動投入しない**。

## 3層の解析（区別は必須）

### A. 明示的な適用・制限条件（事実、入力ごとに出典付き）

- 距離：短距離／マイル／中距離／長距離。脚質：逃げ／先行／差し／追込。馬場：芝／ダート。コース・天候等は別フィールド。
- ゲーム内効果文の `＜中距離＞`、`＜作戦・逃げ＞` など**括弧表示そのもの**を別記録として抽出（複数許容）。全角・半角の表記ゆれは解析時のみ正規化し、元テキストは保持。
- 構造化条件の `running_style`、`distance_type`、`ground_type` 等の**厳格な制限**は括弧表記の有無にかかわらず別記録。括弧表記と構造の不一致は「要照合」、片方へ勝手に寄せない。
- 追加効果のみの条件（例：特定距離なら追加加速）と**基礎効果の発動制限**は別属性。条件付き強化を「その距離以外では発動不可」と誤表示しない。

### B. 発動する状況（構造化条件の事実、分類の証拠付き）

- レース局面：序盤／中盤／終盤／ラストスパート、前半・後半、直線・コーナー。
- 自分の位置／順位：前方・中団・後方、先頭、`order/order_rate` などの具体条件（順位割合・人数の違いは元値を保持）。
- 発動の契機：追い抜き・追い抜かれ、競り合い、近接、他スキルの発動、回復・出遅れ、坂やコース形状、天候等。
- `preConditions`／`conditions` とAND/ORの経路を保ち、タグごとに「制限／機会条件／強化条件／未解析」を付す。未知の `type`、演算子、競合条件が残る場合は未判定。

### C. 実質的な脚質・汎用性（推定、確度と根拠を必ず表示）

- 例：中盤で前方を維持する条件 → 逃げ／先行に**有利な傾向**（脚質の厳格制限ではない）。順位条件・レース人数・展開の差で例外が生じるため、勝手に「逃げ専用」としない。
- 例：後方で追い抜きを要する条件 → 差し／追込寄りの**推定**。他の脚質で発動しないと断言しない。
- 「汎用」は**2項目を分離**：(1) 条件の適用範囲の広さ（距離・脚質・馬場を選ばない）、(2) 発動機会の安定性（特定の順位・追い抜き・坂・他者の行動等に依存するか）。**適用範囲が広い ≠ 発動しやすい**。
- 推定ルールに出典フィールド・規則ID・版・根拠・確度（高／中／低／未判定）を保持。テキストからの単純キーワード検出やLLMの文章分類を無検証で確定値として採用しない。

## 内部データ案（外部マスターのコピーではなくランタイム導出）

`skill_condition_profiles.js`：UmaSim本文を実行時に読み、スキルIDと一致確認した後、分類用の**小さな構造**を生成。原文の丸ごと再配布はしない。

~~~text
skillId
source: revision / numeric ID / name / matched status
explicit: {
  inGameTags: [...], structuredRestrictions: [...],
  restrictionConflicts: [...]
}
invokes: [
  {
    index, preConditions: OR[AND[condition]],
    conditions: OR[AND[condition]],
    effectKinds: [...], triggerFeatures: [...],
    conditionRoles: [...], unknownConditions: [...]
  }
]
analysis: {
  compatibleDistance/Style/Surface: known | inferred | unknown,
  situationalFeatures: [...],
  styleTendency: [{style, strength, basisRuleIds}],
  courseBreadth: known | conditional | unknown,
  activationOpportunity: broad | situational | unknown,
  completeness: complete | partial | unknown
}
~~~

- 実装上は `inGameTags`、`structuredRestrictions`、`inferredStyle` を別にし、UIでは「明示／推定」を常に区別。多段階 `Invoke` の一部のみ解析できても「全件解析済み」扱いにしない。
- 解析対象はスキル効果を確認できる現在のモデル + 明示的な未知区分。スキルID不一致や効果辞書未収録を「制限なし」「汎用」としない。
- 固定辞書版・解釈ルール版をキーにキャッシュし、ソース変更時に再解析。カード検索の操作ごとに2,162件を再パースしない。

## サポカの集約モデル

入力は既存の `hintsByStage[0..4]` と承認済み `card.events`。**同一カードで同一スキルが通常ヒント・イベントから得られても数えるスキルIDは1回**。金・白・○・◎は別IDのまま管理し、関連系列（`lowerId`）の重なりは別指標で把握する。負スキルや未承認 `referenceSkills` は推奨傾向へ無断合算しない。

- **通常ヒントのみ**：指定凸段階で候補となるスキル（確実な入力範囲）。
- **イベントを含む全候補**：承認イベントの全経路のスキルの和集合。ただし排他的結果・未選択経路を**同時獲得できるとは扱わない**。表示上も「潜在的な提供傾向」であることを明記。
- **現在の編成・選択に基づく候補**：既存 `core.directRoutes` で到達・選択状況を反映（既存の到達仕様を再利用）。
- 指標は「条件一致スキルの異なるID数」「既知スキルの割合」「未判定数」「通常ヒント／イベントの内訳」。スキル系列の二重計上に注意。
- 初版は**順位付き総合スコアを採用しない**。抽出・比較可能な実数と割合、推定の根拠を示し、後続で必要なら評価重みを検討。金白の単純な強さ、ヒントLv、実取得確率を混ぜない。
- 分母に未判定を含めて不確実性を表示し、既知だけを分母にした割合も区別。「未判定＝汎用」は禁止。

## UI案（現行のコンパクトなサポカ一覧を維持）

- **カード検索フィルター**：まず距離・脚質・馬場の明示条件と、`明示のみ／推定も含む` の切替。次に折りたたみの詳細条件（局面、位置帯、発動契機、コース要素）を追加。
- **検索意味**：「この距離・脚質で使える可能性のあるスキルが何個あるか」の閾値／割合で絞る。複数選択は同一軸OR、別軸ANDを既定とするが、厳密な個別スキル条件のAND/ORとは区別し、UIで説明する。未知データを無条件で検索一致にしない。
- **アイコン**：カードの識別用画像・名前を小さくしない。最大2種類程度の「強い傾向」を短い文字のチップで付与（例：`逃・先`、`中盤前方`、`汎用寄り`）。明示のみと推定は形状や注記で区別。単独の色に依存せず、カード詳細では分類対象となったスキル・条件・出典を展開表示できる。
- 判定が不十分なカードは無理に上位脚質を選ばず、`判定資料不足` とする。チップが目立ちすぎる場合はフィルター結果または詳細画面のみで表示する。

### A / B / C 検証の基準

- **A（機構）**：条件の括弧内OR、ANDと外側OR、複数 `Invoke`、`preConditions`、効果追加限定、距離・脚質衝突、順位・レース人数、未知型、欠損元データ、ID一致・不一致、通常／イベント重複、排他的報酬、カード凸変更、キャッシュ復元を人工例で検査。
- **B（全件実データ）**：固定ソースの全 `type/operator/value` の分布と解析率を公開し、未対応をリスト化。日本語説明と構造条件の代表ケースおよび難しい反例を手動独立確認。未知条件を隠して「完全」扱いにしない。閾値・推定規則が作る脚質分類の誤分類率を標本・反例で測定して採用判断。
- **C（実環境）**：GitHub Actions Chromiumで検索→カード詳細→出典・明示/推定切替→凸変更→イベント選択→集計→保存復元を試し、Pagesの配信とWindows/Android実端末は別証拠。既存の所持・デッキ・目標・逆引きを壊さない。

## 開発判断の保留事項

1. **分類の深さ**：MVPを明示距離・脚質・馬場＋レース局面・位置で開始し、追い抜き・コース状況は全件型分布を見て第2段階で解放する案。
2. **汎用性の定義**：コース／脚質の適用範囲と、条件を満たしやすい機会を分離する。総合一点スコアは保留。
3. **傾向の評価対象**：通常ヒントを既定、イベントを含む潜在候補は別切替。承認イベントの排他条件と直接獲得を尊重。
4. **表示閾値と確度**：何件・何％でカードアイコンへ表示するか、どの推論を「有力」とするかはP0～P2の全件分布とレビューで決定。根拠なしの固定数値は先行確定しない。
5. **タグの権限**：括弧表記＝ゲーム内明示、構造条件＝資料中の機械的制限、位置による脚質の推薦＝本アプリ独自推定。利用者画面に種類の違いを識別可能にする。

**実装方針**：現行の外部直接取得・IndexedDB・公開イベントゲートに増設する純粋解析モジュールで開始し、いきなり本番のカード・イベントDBを再構築しない。スキル効果本文をリポジトリへ大量複製しない。
