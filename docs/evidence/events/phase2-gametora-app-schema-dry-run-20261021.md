# Phase 2：GameToraから実行時イベントスキーマへの全件試験変換（2026-10-21）

## 目標

既存の[GameTora全2,488イベント中間DB](phase2-gametora-whole-event-normalization-20261021.md)と[1,681数値ヒントID全件照合](phase2-gametora-event-skill-crosswalk-20261021.md)の成果を連結し、実行時アプリが使う`event_schema.js`・`skill_bridge.js`のイベント形式へ変換する。**GameWith全件からイベントDBを作り直さず、GameTora由来の基準データを用いる。**

この作業は**メモリ内での技術的な適合性検査**である。GameTora元のイベント名称・選択肢の原文は保管せず、イベント名・結果名は「イベント003（仮）」「結果1（仮）」等の未承認プレースホルダに置き換える。実行用カタログはディスクに出力せず、**件数・除外理由・カードIDと位置番号のみ**を一時アーティファクトに記録する。

## 全件実測結果

[固定GameTora×UmaSimを使ったGitHub Actions](https://github.com/Nimrodx0/Umasupport/actions/runs/39552469835)で、次の数字を実測（CI成功）。

| 指標 | 件数 |
| --- | ---: |
| GameTora由来のサポートカード（全対象563枚のうち） | 559枚 |
| 入力イベント | **2,488** |
| 元の選択肢 | **4,129** |
| 元の結果経路 | **4,376** |
| **既存アプリのスキーマに変換できたイベント** | **2,084（83.8%）** |
| 変換結果を持つカード | **557枚** |
| 変換を保留したイベント | **404** |
| 変換済みの自動イベント | 609 |
| 変換済みの選択式イベント | 1,475 |
| 変換済みイベントに含まれる数値スキル報酬位置 | **1,413** |
| スキーマ上で保全した明示打ち切り経路 | **88** |
| GameToraに元からないカード | 4 |

2,084 + 404 = 2,488。元カードが4枚欠けていることはイベント0件と解釈しない。また、557枚というのは**少なくとも1つ変換可能なイベントがあるカード数**であり、557枚すべての全イベントが完成したことを意味しない。

### 404イベントの保留理由

| 理由 | 件数 | 対応する方針 |
| --- | ---: | --- |
| `NONSTANDARD_SUPPORT_SECTION_NEEDS_REVIEW` | **257** | 通常・連続以外に分類されたイベントは、出現条件を未確定のまま表示しない |
| `SKILL_ID_OR_HINT_EFFECT_PENDING` | **80** | 固定スキル辞書にないID、補完辞書のみのID、未解釈ヒント等を採用しない |
| `SOURCE_SPECIAL_CASE_REQUIRES_REVIEW` | **27** | 前段結果条件、特殊分岐、直接スキル獲得、非連続の打ち切り等を調査 |
| `CHAIN_PREDECESSOR_NOT_PROJECTED` | **39** | 前の連続段階が除外されたとき、後段だけを「独立したイベント」として表示しない |
| `MISSING_OR_DUPLICATE_RESULT_SKILL` | **1** | 同一結果中のスキルID重複などの不整合を保留 |
| **合計** | **404** | 未対応箇所を隠さず、元の位置と理由を記録 |

この保留は**機械的な変換を止めた位置**であり、GameTora情報がゲームにおいて誤りだと立証したものではない。特殊区分、未対応ID、シナリオ依存の仕様を後続で対応できれば、変換可能件数は増加する。

## 実装内容

- `poc/src/gametora_whole_event_normalize.cjs`：元選択肢の見出しが空文字だったかを1ビット保持する。`label`原文は保存せず、「自動イベント」と「選択肢のあるイベント」を分離する。
- `poc/src/gametora_app_schema_dry_run.cjs`：GameTora中間DBと全スキルID対応を厳格に合わせ、通常の`auto`／`choice`、二つ以上の`outcomes`、結果・選択肢に付く`terminal`、連続した次段階の`requires`へ投影。データ未対応のイベントとそこに依存する後続段階を除外する。
- スキル報酬は厳密に一致した数値IDだけを入力し、元の固定UmaSimスキル辞書を介して**既存の`skill_bridge.prepare`に改めて照合**する。その後、**既存の`event_schema.validateCatalog`で全変換イベントを一度に検証**する。
- `poc/tools/probe_gametora_app_schema_dry_run.cjs`：固定元辞書・カード一覧のSHA-256を照合し、メモリ内の変換と全スキーマ検査を実行。実行用の未承認データは捨てて**統計と除外位置だけ**を出力する。
- `poc/tests/gametora_app_schema_dry_run.test.cjs`：自動・選択式・結果別報酬、失敗時打ち切り、後続の到達／遮断、未対応ヒントと先行イベント欠損の除外、出典の差し替え防止を検査。CIと固定ソースの全件監査に組み込んだ。

## 継続条件と公開上の注意

GameToraのソース掲載順を使って通常の連続イベントの後続候補を作るのは、**GameToraを基準とする既定の解釈**である。実ゲームの現行版で個別に到達を確認したという意味ではない。`sourceOrderAdjacencyVerified:false`と`publicationApproved:false`を維持する。

GameToraの選択肢・イベント名の原文は出力していないため、今回のスキーマ変換だけでは利用者が読めるイベント一覧は完成しない。正式収録には独自の表示文言、レビューにより正確な意味に対応した選択肢名、権利審査、例外のGameWith裁定、公開ゲート通過が必要である。**本番イベントDBの承認済み数は引き続き0件。**

## 次の工程

1. まず変換できた2,084イベントから、**選択肢の意味とスキル報酬を出典に基づいて承認できる小数の実カード**を選び、原文を大量転載せず独自表現で表示可能にする。
2. 第2段階で**GameToraの通常／連続イベントを既存の公開ゲート**（イベントID、選択・結果、前提、公開根拠、ソースハッシュ）へ渡し、初の実イベントを本番DBに登録する。
3. 残った404イベントをタイプ別に進める。特に257の「other」分類は機能範囲を確認し、特殊条件27はGameTora内の効果コードと必要に応じたGameWith裁定で処理する。
4. 4枚のGameTora欠損カードと別資料だけにあるイベントも、網羅性の差分として追跡する。

この段階での**2,084は「スキーマ変換可能件数」であり、ゲームの報酬内容・経路の正しさを最終認証した件数ではない**。
