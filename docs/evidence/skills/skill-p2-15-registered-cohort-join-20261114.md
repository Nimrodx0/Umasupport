# P2.15：実登録JVMスキルと85元AND経路の同一性照合（2026-11-14）

## 問題と研究方針

[元スキルを改変せずに装備したJVM実測](skill-p2-15-registered-source-race-20261114.md)では、固定元辞書の実登録スキルID `105401211` に対し、元RaceCalculatorで3レース／元phase_random条件1,893判定（TRUE3、FALSE1,890）／元モデル技能イベント3件を観測した。

一方、[アプリ照合済みの元85経路](skill-p2-15-rank-random-same-and-handoff-20261113.md)は、`order_rate`＋`phase_random`が**同じ元Invokeの現在条件AND**に含まれる85スキルから抽出したものである。これら2つの研究は独立に実行されており、IDだけで「元のAND条件が同一」とは言えない。たとえ条件型・Invoke番号・AND数が一致していても、他の述語型や元数値パラメータが異なる可能性がある。

## 厳密な照合方法

1. [元Kotlin登録スキルJVMテスト](../../../poc/source-probes/P215RegisteredSourceSkillRaceTest.kt)で、実際に装備した**元`SkillData`の全Invoke**について、元Invoke番号、`conditions`全OR・AND要素、`preConditions`全OR・AND要素を順番ごとにシリアライズする。各述語は`[type, operator, value]`の順で表し、全構造をコンパクトJSON配列として**SHA-256**を計算する。**元の条件全文・数値は成果物へ記載せず、ハッシュだけを残す。**
2. [独立したアプリ照合器](../../../poc/src/skill_p2_15_registered_cohort_join.cjs)で、固定スキル辞書の読み込みから作られた元アプリモデルを再利用する。元の全Invoke条件・値を同じ規則で別途SHA-256計算し、元JVM観測指紋と比較する。
3. **元スキルID、Invoke番号、元OR行インデックス、元AND述語数、元事前条件OR件数、元条件論理全体SHA-256**が一致し、かつ85候補の**同一元AND経路**に存在する場合だけ、「元条件構造と数値の同一性照合ができた」と記録する。候補が存在しない・異なる場合は、その差を欠落や相違として記録し、適当な別スキルの結果を転写しない。
4. [固定元スキルCI](../../../.github/workflows/skill-condition-inventory.yml)で、元818照合スキル／970経路／85候補／2カーネルとの整合と、**真の順位条件観測0件、元全AND実測0件、正式適性0件**をテストする。固定元JVMを再実行する[登録スキルテストCI](../../../.github/workflows/p2-umasim-registered-source-skill.yml)で、そのSHA-256の出典が元の`data/skill_data.txt`であることを照合する。

独立した別CIの実測を**同じレース・同じtickの複合観測と誤認しない**。元Kotlin側で`order_rate`は無視されるため、たとえ全条件の指紋が一致しても「元順位率ANDが成立した」ことにはならない。9頭・12頭の順位率条件の既存表は、二次資料のモデル解釈に基づく算術表であり、元UmaSimの順位率実装またはゲーム公式仕様ではない。

## 照合結果と対象選択の変更

[**PR #445の固定アプリ辞書inventory CI #43463278660**](https://github.com/Nimrodx0/Umasupport/actions/runs/43463278660)では、前回の元JVM観測スキルID **`105401211` はアプリ側818照合スキルに存在せず、85個の元順位率＋ランダム窓AND候補にも存在しない**ことを確認した。したがって、前回の元モデル実測1,893件を85個の元スキルの実測に計上しない。

一方、固定アプリ監査では、85経路／85スキル／2共通カーネルを確認し、その最初の候補スキルIDは`200541`、`200542`、`200571`、`200572`、`200591`、`200592`等である（**代表候補であって、ランダム窓が実際に観測できたという意味ではない**）。

このため、[元JVMワークフロー](../../../.github/workflows/p2-umasim-registered-source-skill.yml)を改訂して、固定辞書の全件監査から得た**85スキルのID集合を同じCI実行内で生成し、そのIDを含む元登録スキルだけを選べる**ようにした。元の`phase_random == 2`をANDに持つものについて、JVM本体で抽選を観測したのち、元の全Invoke条件SHA-256を[独立照合器](../../../poc/src/skill_p2_15_registered_cohort_join.cjs)で検証する。

[**同じ固定元85候補を抽出し、元JVMを実行して独立照合した成功CI #43465317158**](https://github.com/Nimrodx0/Umasupport/actions/runs/43465317158/job/132022764535)の観測では、85経路内の**元登録スキルID`200671`** を選び、元`SkillData`全Invoke論理式のSHA-256指紋（`6e27fd1a1e4394c7a117ec0176e8fade207f0b3983b64c41405c71d4602ec175`）が、元JavaScript照合器の独立計算と**一致**した。元アプリ固定辞書の候補と**元スキルID・Invoke1・条件OR行0・AND述語3・事前条件OR0・全元条件指紋**が一致することを確認した。

| 指標 | 固定元データと元JVM実測 |
| --- | ---: |
| 固定アプリ元スキル全体／元条件照合／未照合 | **881／818／63** |
| 元の`order_rate`＋`phase_random`同一AND候補 | **85経路・85スキル・2共通カーネル** |
| 実JVMランタイム観測かつ同じ元AND指紋を確認した代表スキル | **`200671`、1スキル** |
| 元JVMでのレース計算 | **3レース** |
| 元`phase_random==2`の判定呼び出し | **2,040フレーム** |
| ランダム区間内でTRUE／外でFALSE | **3／2,037** |
| 元UmaSimモデルでの技能イベント | **3件** |
| 元`order_rate`の元JVMでの判定／元全AND成立の実測 | **0／0** |
| ゲーム発動確率／P3/P4正式適性 | **0／0** |

試行別に元チェックが **709（真1／偽708）、675（真1／偽674）、656（真1／偽655）フレーム**。2,040回は元条件関数呼び出しの回数であり、独立した2,040回のスキル試行・実ゲーム確率ではない。イベント3件も**元シミュレータ上の元登録スキルのイベント**であり、本物のウマ娘の発動率ではない。

元順位率条件は元UmaSimで未実装のため、すべての元条件に実測が揃ったと解釈してはいけない。**順位率算術表は別モデル資料に基づく推論**として次の意味に限定する：元ID`200671`の順位率条件に対して、モデル9頭では**6～9位が真、1～5位が偽**、モデル12頭では**7～12位が真、1～6位が偽**という閾値判定候補が得られる。これらは元UmaSimレースの当該2,040フレームに対応する順位を測ったものではない。

CIで実際に条件指紋が一致する1スキルを得たため、他84スキルの元抽選結果・成立率を複製せず、**1つの共通判定機構の再利用可能性が具体的な元スキルで確認できた**。

## 次工程

同一性を確認できた場合、実レースの同じ元判定時刻における元`phase_random`を必要条件として保持しながら、`order_rate`の真偽を外部の独立順位推定器から得る方法を検討する。ただし、元UmaSimは1頭の走行を計算しており9／12頭の**実順位は内生的に観測されない**。元レース位置から順位を単純に作らず、同時走行・競争相手の仮定やゲーム仕様に関する不確実性を明示する。今回の同一性確認だけでは実発動確率、脚質・距離・芝ダートの非明示的成立機会W、P3/P4適性を計算しない。
