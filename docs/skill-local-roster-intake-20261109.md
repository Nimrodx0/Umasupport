# P2：実対戦9頭の脚質構成をローカル記録する研究用手順（2026-11-09）

**状態：ローカル収集器と人工テストを実装。実対戦の新規観測データはまだ取得していない。P2の4脚質・発動条件、P3均衡編成基準、公開アプリのデータは不変。**

[実対戦同時編成の公開根拠監査](skill-real-joint-roster-evidence-20261109.md)では、9頭の同時脚質構成がわかる公開観測は1レースしかなく、過去3大会の各240頭の「相手6頭の脚質別総数」から9頭の共同分布は復元できないと確認した。このため、**同一大会・同一ラウンドで、試合ごとに9頭全員の4脚質人数がわかる**入力経路を、公開Webアプリとは切り離して用意する。

## 収集の目的と対象

- 対象：**チャンピオンズミーティングの9頭対人レースだけ**。LoH（12頭／NPC）や別のゲームモードは自動流用しない。
- 1行＝**実際に観測した1試合**。自分の3頭の逃げ・先行・差し・追込の人数を4整数で、対戦相手の合計6頭を別の4整数で記録する。両者を加えた9頭を派生する。
- 1大会の中でも、リーグ／ラウンドの違いは別コホートに分ける。参加しなかった試合や不明な出走者をゼロとして補完しない。
- 記録するのは**4脚質の人数のみ**。出走者名・ユーザー名・プレイヤーID・画像・対戦ログ全文・正確な時刻・プロフィールURLは不要であり、CSVとして読み込まない。
- 大逃げの独立確認は `oonige_check` 列で **`verified-none`**（そのレースに大逃げがいないと個別確認できた）か **`unknown`**（未確認）を選ぶ。大逃げがいた場合も独立の人数内訳を本形式は保持しないため **`unknown`** とし、4脚質GlobalSimと同じ分類であると宣言しない。
- `captureMethod` が `consecutive`（事前に決めた全試合を順次記録）、`selected`（任意に選択）、`unknown` のどれかを申告する。これは**入力者の申告**で、独立した観測検証にはならない。

## 手元での使い方

実行条件はNode.js 22以降。**このツールにネットワーク通信・アップロード機能はない**。出典元や権利が確認できない第三者画像・ログを入力したりGitHubへ公開したりしない。

1. リポジトリのルートで `mkdir -p poc/private-rosters` し、[CSVのヘッダーだけのテンプレート](../poc/examples/private-roster-nine.template.csv) と [コホート情報テンプレート](../poc/examples/private-roster-nine.metadata-template.json) を `poc/private-rosters/` にコピーする。このディレクトリは `.gitignore` に追加する。
2. CSVの各行へ、同一試合の `race_key,own_nige,own_senkou,own_sasi,own_oikomi,opp_nige,opp_senkou,opp_sasi,opp_oikomi,oonige_check` を入力。**`race_key` は自身の記録内だけで重複しない、個人情報ではない `race-001` など**。ゲームのマッチIDやアカウント番号は使用しない。自分3頭＋相手6頭の計9頭に一致しなければ拒否する。
3. コホート情報の `eventMonth`、`round`、`captureMethod`、`cohortId` を実際の観測条件へ修正する。`expectedRaceCount` は事前に対象数が決まっていた場合にその数を、未定なら `null` を入れる。予め宣言した試合数に足りない場合は「不足」として明示される。
4. 実行：

```sh
node poc/tools/skill_local_roster_intake.cjs \
  poc/private-rosters/cohort.json \
  poc/private-rosters/races.csv \
  poc/private-rosters/derived-summary.json
```

出力ファイルが**既に存在する場合は上書きせずにエラー**となる。誤上書きを防ぐため意図的に `wx` 作成と、対応OSで可能な限り所有者だけに読めるモードを使う。

**CSVの例（人工データ、実際のレースではない）：**

```csv
race_key,own_nige,own_senkou,own_sasi,own_oikomi,opp_nige,opp_senkou,opp_sasi,opp_oikomi,oonige_check
local-001,0,1,2,0,1,3,1,1,unknown
local-002,1,1,0,1,0,3,2,1,verified-none
```

`race_key` の重複、列の増加、文字列の出走者名、引用符つきCSV、負数、小数、未対応ラウンド、9頭・6頭の混同はエラーにする。この第一版は「厳密なカンマ区切り・1行1レース」の最小形式であり、Excel等からの汎用CSV変換器ではない。

## 出力と意味

派生JSONには、次の**人数集計だけ**を出す。

- 自分3頭の脚質別総数、相手6頭の脚質別総数、9頭全体の脚質別総数。
- 観測した9頭の**編成パターン別の試合数**。総試合数が30未満なら割合表示を `null` にする（過度な確率表現を避けるための表示上の制限で、30件以上の一般化を保証する統計閾値ではない）。
- 「9頭全体で逃げ不在の試合数」と「相手6頭で逃げ不在の試合数」は**別々**に出す。他の脚質も同じ。
- 未確認の大逃げが含まれるレース数、事前に申告した観測件数との一致・不足、観測の抽出方法。
- 生CSVの**`race_key`や行そのものは出力しない**。成果物に個人名などは含めない設計だが、入力の内容・元の著作権・公開権利は利用者側で別途確認が必要。

**観測の意味**：仮に30レース以上集まっても、その出力は「そのコホートで記録された試合の記述統計」にすぎない。多数の試合が同じ相手を含む可能性、特定プレイヤー・育成環境・ラウンドの偏り、記録漏れがあるため、「全ユーザーの同時編成の確率」とはみなさない。相手6頭の実測度数の数値を入力しただけで、9頭の完全な編成を復元することもできない。

## P2／P3へ導入する条件（**未承認**）

自分の複数試合が記録された後も、以下の条件を満たすまで、その結果をP3標準評価へ自動投入しない。

- ゲームモード・ラウンド・開催月・人数・大逃げの対応関係が確認できる。
- 収集元の許可・個人情報・第三者の権利・同一試合の重複観測について整理できる。
- 偶然標本・代表標本と呼べるかを、抽出設計の根拠で説明できる。
- 取得データの数値・誤差・モデルとゲーム版の差、脚質別の成立機会評価の許容範囲を検討する。
- 利用者が別途、編成別表示またはP3での扱いを承認する。

**現時点では標準評価は9頭「逃2・先2・差3・追2」、12頭「各脚質3頭」の均衡編成を維持**。高／中／低の閾値や脚質特異性、サポカ集約も変更しない。

## 検証の区別

- **A 機構**：[取り込み器](../poc/tools/skill_local_roster_intake.cjs)と[人工テスト](../poc/tests/skill_local_roster_intake.test.cjs)で、人数合計、異常値、匿名キー重複、ラウンド、未確定大逃げ、30件未満の割合 `null`、レース単位の不在数と相手6頭の不在数の違い、出力に生データが漏れないことを検証する。
- **B データ**：実レースの追加CSVは未入力。前回の[実対戦公開記事の証拠監査](skill-real-joint-roster-evidence-20261109.md)から実観測の9頭同時編成1件・別標本の相手6頭×40戦周辺度数があることだけ確認済み。
- **C 実環境**：観測時のゲーム画面での誤入力や大逃げ識別、マッチング重複、実機でのCSV入力操作・公開アプリ連携は未確認。研究CLIのテスト成功を実対戦確認とみなさない。
