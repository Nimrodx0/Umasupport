# 仕様・実装・テストの整合性監査：初回（2026-10-22）

## 目的と判断の序列

今回の起点は、**GameTora固定元→元サイトを確認→GameWithを疑義裁定に使用するという既存のユーザー決定が文書化済みだったのに、作業中に「さらに第二の独立サイトやゲーム実測を要する」という条件が暗黙に追加されたこと**である。ルールを細分化して増やす前に、ユーザー決定・設計・コード・テスト・CIの期待値が一致しているかを調査する。

[文書運用規約](documentation-policy.md)に定める序列を維持する。**ユーザーの最新決定と現在の要件**が「何を作るか」の判断材料、コードは「現に何が動くか」の証拠、テストは「何を期待値として固定したか」の証拠であり、**CI PASSだけで仕様適合やユーザー承認は証明されない**。設計の改善を提案することと、合意済みの必須条件を変更することは別。開発上の仮説から必須条件への格上げを黙って行わない。

今回はイベントソース・結果依存・開発版設定・公開ゲートの**4領域のスポット監査**であり、レポジトリ全コード／全決定の網羅監査ではない。対象ファイル名を明示し、未調査箇所について「矛盾なし」と主張しない。

## 根本原因についての分析と未証明部分

- **観測できた仕組み上の問題**：テストの期待値が旧実装から作られると、利用者の判断に反する実装をCIがPASSで補強してしまう（C-01）。また、実装を更新しても現在要件を訂正しないと、新しい担当AI／Codexがもう一度同じ開発を計画し得る（C-02）。ユーザーが維持不要とした処理がテスト経由で事実上「壊してはいけない機能」に見える（C-03）。
- **推論上の原因仮説**：直近の局所課題を解こうとする際に、AIが設計の補助的仮説を必須条件へ暗黙に昇格させている可能性。このメカニズム自体の証明は、現時点のリポジトリ証拠だけからはできない。
- **根本方針**：ユーザー決定と独立した「開発上の提案」は、ユーザーの承認なしに採用条件や完成条件を変えない。矛盾が見つかったらコード・テスト・文書のどれを正しいとみなすかを直感で決めず、**決定の出典と時点／矛盾位置／合意済みか否か／影響範囲**を先に照合する。

## 継続監査における整理方法（提案であり新しい製品仕様ではない）

一件ごとの記録は `決定へのリンク → 実装箇所 → テストで固定した期待 → 差異の分類 → 対応範囲` の順で保持する。差異は少なくとも次を混ぜない。

1. **決定違反**：コードやテストが明示された最新のユーザー決定と反する。ここで「さらに検証してから」と採用基準を変えてはいけない。
2. **事実上の陳腐化**：コードが進んだのに要件文書・設計文書の実装状態が古い。仕様変更ではなく実装済み事実を訂正する。
3. **許容された実装余剰**：必要ではないが存在する機能。保守・削除の判断は別であり、違反とは呼ばない。
4. **本当の新要件提案**：現行決定にない制約・完成条件が必要と考えた場合。**承認なく新しい必須ゲートにしない**。
5. **資料不足／調査未完**：判断する必要がある事実が未確認。未確認である具体的位置と、現行基準での欠落を記録する。

現段階ではこの分類法に対して、新しい全レポジトリCI強制やGitHubブランチ保護を勝手に導入していない。汎用の要件トレーサビリティを自動化するには、**ユーザーが承認した要求の識別子と、ソース・テストへの追跡可能な結びつき**が必要。コード／テストへのリンクが存在するかだけを機械検査しても、「ユーザーが要求した意味と合致するか」は自動で立証できない。

## A/B/C と対象の限界

- **A（実装根拠）**：結果条件 `outcomeId` の検証・到達計算と、移行関数の現存をコードで確認。テストファイルに対象の期待値があることを確認。今回新しいロジック変更・新たな自動化はしない。
- **B（仕様根拠）**：最新要求 `requirements.md`、ユーザー決定 `decisions.md`、文書規約とイベント採用決定を照合。ユーザーとの過去会話を機械的に全文監査したわけではない。
- **C（環境）**：今回は文書の事実訂正と監査であり、新しい実ゲーム・物理端末試験を行っていない。PRの通常CIが通ってもレポジトリ全域の整合性監査完了にはならない。

この文書は**ユーザーの決定・機構設計・正式公開条件を変更しない**。旧設定移行ロジックは保留。次の対象領域として全カード収録・サポカ通常ヒント・UI／保存・公開データの各経路へ同じ観点の監査を広げることは可能だが、「全件合格」の前提を置かない。
