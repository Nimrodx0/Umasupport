# 検証計画・工程完了ゲート

本書は**将来に適用する検証基準**の正本です。旧実績・休止工程は [検証履歴](verification-history.md) に分離。関連：[ロードマップ](roadmap.md) / [要件](requirements.md) / [CI](../.github/workflows/ci.yml)

## 1. 目的と基本原則

機能が少数のサンプルで動くことは**機構の試験結果**であり、データ全件性や実機品質の証拠ではない。各工程では開始時に検証対象の母集団、例外の扱い、合否基準、実施手段を決める。実装後に都合のよい成功事例だけで完了判定しない。

工程ごとに以下の3軸を別々に評価する。

| 軸 | 何を保証するか | 代表的な証拠 |
|---|---|---|
| A. 機構（ロジック） | 仕様、不変条件、異常系、データ更新への挙動が正しい | 単体・回帰・結合テスト、型／スキーマ検査 |
| B. データ（網羅・正確性） | 対象全件が分類され、ID・経路・例外と独立根拠が追跡できる | 全件監査、未照合一覧、出典・版・ハッシュ、独立照合 |
| C. 実機（利用者の体験） | 配信された同じコードが実ブラウザで正しく読込・表示・操作・保存できる | Pages上の操作手順と期待値・実測値、環境・日付・コミット記録 |

- **ゲート通過**：スコープ内の必須項目がA/B/Cをすべて満たし、影響のある未解決がゼロ、または変更されたスコープと許容理由が要件・意思決定ログへ明記されている場合に限る。
- **部分実装**：1軸でも必須項目が未実施なら「部分実装／検証待ち」。別の軸の合格で代替しない。
- **未解決の扱い**：不明を「なし」に変えない。未収録・取得失敗・未照合・実際に存在しない根拠付きを別の状態として記録する。
- **ソースの真実性**：「入力ファイルに何件あったか」と「ゲームの現行全体に何件あるか」は別。独立分母を得られない場合は真の網羅率を数値化しない。
- **検証と権利**：技術的に取得できても利用可能とは限らない。公開権利・転載範囲・アクセス負荷の判断は公開ゲートに含む。

## 3. Phase 1：スキル辞書・上下関係の検証

- 取得元の版・ハッシュ・スキル／サポカID集合と、金白・○／◎の構造を固定したうえで比較する。**旧時点の件数を現在の分母として再利用しない**。独立の実データ照合が終わっていなければ検証未完とする。
- 異常系は同名異ID・ID衝突・不正スキーマ・未収録・古いキャッシュ・取得失敗を含める。直接提供と間接カバーの重複計数を防ぐ。
- 実環境では公開Pagesのデータロード、キャッシュ復帰、階層表示、デッキ・目標への集計を対象端末とコミットを記録して検証する。最新の実施状態は [status.md](status.md) と [金白監査](evidence/skills/skill-hierarchy-coverage.md) を参照する。

## 4. Phase 2：イベント網羅と公開の検証

1. **母集団**：対象カード集合・版・出典を事前固定し、元データ上のレコード数と実ゲーム全体の収録率を区別する。元資料だけで分母が確定しない場合、完全性を宣言しない。
2. **同定**：カード／イベントID、通常・連続、選択肢・排他的結果・スキルID／Lv・内部後続条件を別々に検証し、資料にない分岐を創作しない。
3. **承認・公開**：出典・版・利用方法と第三者表現の権利を確認し、承認済みカタログと非公開候補を分離する。**既存2,512件を1件ずつ人手承認する手順は主工程ではない**が、個別例外と公開ゲートは省略しない。出典の数値差は [例外裁定契約](event-adjudication-enforcement.md) に従い、公開可否とは区別する。
4. **記録**：固定技術変換、公開承認、保留例外、実ゲームの正確性・網羅性を分け、結果は [status.md](status.md) と個別監査に保存する。

公開の独立ゲート：第三者JSON・文章・画像のそのままの配布はしない。適切に編集した独自数値事実でも、出典の利用条件と適切な公開検証は別途必要。**現行の`verify_event_release.cjs`はイベント別の旧公開形式に対応する既存CI**であり、一括配信・参照方式を無承認で公開する抜け道にはしない。全件の人手署名を主工程から外しても、提供方法と出典条件の確認は省かない。取得・構造化成功を自動公開とみなさない。

**機構と実運用の区別**：新カード判定の `derived_github_new_card_source_plan.cjs` に加え、既存の全イベント変換器を再利用するアダプタ、JSON受入検証、日次保留Issue更新は実装済み。ただし2026-10-29実新カード3枚は派生JSON未掲載で、**対象新カードの実イベント変換・編集承認・公開DB追記は未達**。[実測](status.md)を参照。GameTora HTML取得器の未解析件数は4Bの合否と無関係。

## 5. 実ブラウザ・端末の受け入れ計画

**ここは合格基準です。実施済み・未実施の判定表ではありません。** 現在の実施状況は[status.md](status.md)、実測の根拠はPR・CI・対象監査、[旧検証表](verification-history.md#旧ブラウザ受け入れ表当時の測定結果)を参照します。

| 試験対象 | 確認すること |
| --- | --- |
| 公開Pagesの新規プロファイル | 通常ヒント・スキル辞書・公開イベントの正しい取得、明示的な失敗表示 |
| 元データ遮断・復帰・キャッシュ破損 | 検証済みキャッシュだけを使用し、設定を破壊せず回復する |
| デスクトップ・スマートフォン実機 | 主要UIの識別・操作・比較・集計に致命的な問題がない |
| イベント結果・連続内部条件 | 選択肢／結果の排他、打ち切り・後続依存、未設定の扱いが仕様どおり |
| デッキ・目標・設定 | 本育成／継承育成の独立、保存・JSON入出力・復元・異常時の保護 |
| 表示幅・ブラウザの差 | 利用者の対象環境で重大な互換問題がない |

各結果には**検証日、デプロイコミット、OS・ブラウザと版、操作・期待値・実測値、Pass／Fail／未実施、根拠リンク**を残します。ヘッドレスChromiumの成功とWindows／Android実機の成功を同じものとして扱いません。キャッシュからのデータ復帰とHTML/JSを含む完全オフライン動作も区別します。

UIのみの変更等、B軸に新しいデータがない場合は「対象データなし」と理由を記載し、関連する既存データの非回帰をA/Cで確認する。単に空欄・未実施のままPassにしない。
