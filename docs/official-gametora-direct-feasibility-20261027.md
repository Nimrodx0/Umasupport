# GameTora本体の直接取得実現性：少数カード技術検証（2026-10-27）

## 目的と非対象

[直接取得移行の現行方針](upstream-refresh-operations.md)に従い、第三者GitHubの派生JSONを本番更新資料に必須としない構成にできるか、**最初はわずかなカードだけ**確認する。GameTora本体を「ゲーム開発元の一次資料」とは呼ばず、GameTora派生JSONより直接のサイト出典として扱う。

- 静的HTTP応答検査：固定対象3枚のみ、既存SSR `30001`、新規SSR `30322`／`30323`。
- ブラウザ表示検査：既存SSR `30001` のみ。URLから追加カードを検索・巡回しない。
- [限定ソース検証ワークフロー](https://github.com/Nimrodx0/Umasupport/actions/runs/40464401966) でGitHub Actions上のNode 22とChromiumを実行した。
- 本体HTML・JSON・イベント名・選択肢・報酬原文・画像・スクリーンショットはGit履歴、Actionsアーティファクト／ログへ保存しない。確認したのはカテゴリ見出し、JSのデータ形式、数値による構造シグナルだけ。

[Chromiumの実地結果](https://github.com/Nimrodx0/Umasupport/actions/runs/40464401966)（カード30001だけ）：

- ページ表示中の同一サイトXHR／fetchは38件、そのうちJSON応答27件（同じ27件の応答をメモリだけで形状検査）。初期HTTP本文では足りない情報がクライアント側で動的に表示されることは確か。
- JSON応答27件のうち、イベント関連の名前を持つ項目が見つかった応答は8件。ただし **`choices` 配列・`outcomes` 配列・イベントらしい `choices` と `section` の組合せは0件**。4件には `effects`／`rewards` らしい配列名があったが、これだけでイベントの結果構造やスキルの意味を証明しない。

- 403/429は未観測。ネットワーク越しの動作が少数件で成功したことは、大規模な定期自動アクセスの許諾やサイトAPIの長期安定性の証拠ではない。

比較用の歴史的固定 [GT派生JSON `support_30001.json`](https://github.com/systemless10/UmamusumePS/blob/6e38b54af4fad397ff4491e63007a90705a4fe67/server/data/events/gametora/support_30001.json) にはイベント5件（連続3件・ランダム2件）。[GameTora本体の該当カードページ](https://gametora.com/ja/umamusume/supports/30001-special-week)にも連続3件・ランダム2件の一覧が表示される。しかし**選択肢／ヒントLv／報酬数値／結果分岐／打ち切りの全件同一性は未確認**。2026年10月26日新カードの派生JSONが欠損していても、本体ページの掲載状況を別途確認できる。

## 収穫と次の工程

**確認できたこと**：元サイトの閲覧は一部のカードについて現行GitHub Actionsから可能。ページ情報はJS描画にも依存し、初期JSONやJSONレスポンスの浅いキー走査だけではイベント経路の完全情報を得られない。

**解決していないこと**：

1. UIに表示されるイベント一覧と、クリック後の選択肢／結果の構造が、DOMまたはページを構成する通信データのどこから提供されているか特定する。少数カードの通常の閲覧経路を使い、検証済みカードIDと選択肢・結果を取り違えないこと。
2. 正式に提供される安定API／低負荷のアクセス方法と、取得・継続運用の利用条件を確認する。アクセス制限を回避しない。サイトから大規模にデータを抽出して配信する前提を置かない。
3. 実取得内容が利用可能と判断できた場合、変換器のイベントID・カードID・選択位置・結果位置・報酬数値ID・連続分岐を旧固定GTと独立照合する。過去のGT派生元は比較用資料として維持する。
4. 上記のA機構／Bソース実証／Cブラウザ回帰を区別して本番の出典変更PRを行い、イベント原文・画像の配布や公開承認は別に検査する。

**未実装**：GameTora公式HTMLの実イベント正規化アダプタ、正式な継続更新ジョブ、データ承認／公開への自動反映。既存の固定派生GT元とレビュー済みイベント0件の状態は不変。

## 追加実験：公式サイトの数値報酬をイベント別に照合（2026-10-27）

[実ブラウザでの候補報酬比較](https://github.com/Nimrodx0/Umasupport/actions/runs/40469880077)で、引き続き既存カード30001の同一1ページ・5イベントだけに限定して、各パネルに描画された数値テキストを暫定的に「種類・増減量」の組に変換した。[読み取り器](../poc/src/official_gametora_numeric_fact_parser.cjs)はスピード／スタミナ／体力／ヒントLv等を区別し、読み取れない形式を**未分類**に残す。原イベント台詞・選択肢・記事の原文・ゲーム画像をGit／ログへ出さない。

検証中、複数イベントが同じパネル領域を使用していることが判明。クリック直後に次のイベントのデータを読もうとすると**前のイベントの値を誤って引き継ぐ**ため、イベントボタンを都度開いて画面更新を待ってから抽出する処理に修正した。最初の取得で見えた大きな数字の不一致をそのまま元サイトの誤りと断定しない。

| 観点 | 単一カード30001での実測 |
| --- | --- |
| 対応が確定したイベント見出しと分類 | 5/5 |
| 固定派生元にある数値効果の出現 | **36件** |
| 公式画面の日本語表記から種類・増減を判定できた効果 | **28件** |
| 数値の種類・符号・値が元データの効果に一致 | **28/28件** |
| 認識済み効果に旧データと異なる数値がある | **0件** |
| 元データに存在し、現行DOMパーサで認識できていない効果 | **8件（すべてbond／絆ゲージ系）** |
| 通常イベント・連続イベントを通じたヒントLvの数値出現 | **5件、一致** |
| ヒント対象の実スキル数値ID | **未照合** |
| どの選択肢／成功結果に対応するか | **未照合** |
| 連続イベントの打ち切りと後続依存 | **未照合** |

**重要**：絆ゲージ効果の未認識8件は、元サイトに情報が存在しないと判定したものではない。サイト上の表現の差、DOM構造、抽出器の未対応等を区別できていない。スキル計画に必要なヒントLvだけ先に一致しても、スキルID／どの選択肢から得られるかを紐付けずに公開・集計へ使用することはできない。

検証軸は **A：** 単純な効果テキストと未解析・多重数値の人工テスト、**B：** GameTora本体1カードの実描画と固定歴史的参照の数値照合、**C：** GitHub Actions上の実Chromiumでの表示・クリック。全カードでの実データ一致・スキルID照合・公開・実ゲーム内取得確率は未検証。本実験の数値比較はメモリ上のみで、本番独自DB・GitHub Pagesの承認済み実イベント0件を変更しない。

### 次の具体的な処理

1. 描画済み効果の前段の構造（選択肢番号／結果番号）を確定する。選択肢2件と成功／大成功2件は同じ「2行」ではない。数値事実の順番だけで経路を推測しない。
2. スキル名が画面にあれば、原文転載なしにUmaSimの数値スキル辞書へ**一意対応**させる。同名別IDや金白を安易に統合しない。
3. 連続の chain_end 相当の例外を公式サイトの掲載事実で確認し、未記載なら現在の規則に従った通常継続と、未確認の特殊条件を分離する。
4. 全イベントの経路単位の差分を取得できるまで、固定参照を削除しない。サイトのアクセス条件と長期取得方法を確定した後にだけ本番データ更新へ昇格する。

## 追加実験：結果経路単位の効果・数値スキルID・ヒントLv照合（2026-10-27）

[5イベントを経路別に比較した実ブラウザ検証](https://github.com/Nimrodx0/Umasupport/actions/runs/40473532989)では、旧GT固定サンプルは合計9結果経路で、直接GameTora本体の画面から得たグループは8件。うち4イベント・7経路が、数値効果の種類・増減と、独立UmaSim辞書から特定したスキルID・ヒントLvの**グループ署名**で一意に対応した。

| 対象 | 元の経路数 | 最初のDOM抽出で認識した経路グループ | 個別グループの対応状況 |
| --- | ---: | ---: | --- |
| 通常イベント（旧イベント1） | 2 | 2 | 2経路とも一意一致 |
| 通常イベント（旧イベント2） | 2 | 2 | 2経路とも一意一致 |
| 連続イベント（旧イベント3） | 1 | 1 | 1経路が一意一致 |
| 連続イベント（旧イベント4） | 2 | 2 | 2経路とも一意一致 |
| 連続イベント（旧イベント5） | 2 | 1 | **未照合、二結果が1つの画面グループ** |

旧イベント5の実DOMを追加で確認したところ、単一パネル内に複数の結果候補を区切る **OR 表示** が存在する。試験コードでは実際に可視のOR区切りが一意にある場合だけ分割することとし、旧データの結果数から逆算して分割しない。候補グループの一対一対応が曖昧な場合も保留する。

**解釈の境界**：報酬の組合せが一致することと、「一方が選択肢、もう一方が成功・失敗」「前段で打ち切る」等のゲーム上の意味を確定することは別。`visualGroupSemanticsVerified`、`choiceAndOutcomeLabelsVerified`、`explicitChainTerminationVerified`、`publicationApproved` はfalseを維持する。旧固定データは参照用に使うだけで、GameTora本体から未確認の数値IDや経路を逆算して取り込まない。

関連実装：[試験用の経路署名比較器](../poc/src/official_gametora_route_group_probe.cjs)と[その合成試験](../poc/tests/official_gametora_route_group_probe.test.cjs)。この結果だけで全カード・全経路の自動収録や、ゲーム内分岐の正しさは証明できない。

## 選択肢／OR結果と連続打ち切りの区別（2026-10-27）

[GameTora本体の限定ブラウザ検証](https://github.com/Nimrodx0/Umasupport/actions/runs/40477838405)では、既存SSR30001の5イベントについて、参照GT由来の「プレイヤー選択肢数」=画面上のトップレベル表示グループ数が各2／2／1／2／1で一致した。結果経路の個数は各2／2／1／2／2。最終連続イベントではトップレベルの1グループ内に可視OR区切りが1箇所あり、2結果に分岐していることを、前段の[9/9経路署名照合](https://github.com/Nimrodx0/Umasupport/actions/runs/40474474931)と別軸で確認した。
